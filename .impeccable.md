## Design Context

### Users

One GM and five to six invited friends use arken-space in desktop browsers during real tabletop sessions. The GM prepares scenes and controls hidden information; players need to enter quickly, read their character state and act without learning a complex tool.

### Brand Personality

Dark fantasy, immersive and carefully crafted, with clear and dependable everyday interactions. The owner's direction on 2026-09-10 makes visual quality and the basic game experience the immediate priority, not a later branding phase.

### Aesthetic Direction

Use the owner's [Game UI — Dark fantasy RPG reference](https://www.figma.com/design/OCg3Y59HNzKaBijRhxsVAZ/Game-UI-Dark-fantasy-RPG--Community-) as the visual starting point. The reference has not yet been inspected or translated into an approved visual brief; specific colors, fonts, motifs and assets are not decided by this document. Do not substitute an arbitrary generic fantasy palette for that review.

Keep the map prominent and the game state legible. Direct labels, visible focus and selection, clear action hierarchy and restrained motion remain essential. Adapt the reference to a dense, web-first VTT rather than copying a game's HUD without regard for keyboard use, smaller viewports or GM/PLAYER permissions.

This direction supersedes the earlier neutral-prototype-only approach. First align the visual direction on the main game screen, implement the connected core flow and verify it as a whole; secondary backend and infrastructure work follows, rather than displacing this work.

### Design Principles

1. The current game state must be understandable at a glance.
2. The map gets priority over navigation and chrome.
3. One obvious action is better than a flexible but hidden control system.
4. GM and player permissions must be visible as well as enforced.
5. Atmosphere and visual craft belong in this phase, but must not hide actions, consume the journal's reading space or obscure essential state.
6. Actions, pending feedback and errors must identify their character and initiating control. Changing the viewed character must not relabel a previously accepted action.
