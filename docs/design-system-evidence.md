## Примеры системного эффекта

1. **Одна модель темы для API и веба.** Генератор читает один набор палитр и выпускает CSS, веб-описание и контракт. Не нужно вручную поддерживать три списка допустимых тем.
2. **Общие примитивы вместо отдельных реализаций экранов.** `Button`, `Dialog` и `Popup` задают переиспользуемые состояния и правила фокуса. Старый слой кнопок ещё участвует в каскаде ([legacy CSS](../apps/web/src/ui/legacy-button.css)); его удаление — отдельная миграция, не свершившийся факт.
3. **Проверяемая граница для сложных панелей.** Инвентарь оверлеев и тест закрытия помогают заметить, когда новый поповер меняет зону ответственности или поведение соседней панели. Времени, сэкономленного системой, не измеряли.

## Компоненты, состояния и сложные паттерны

| Паттерн                   | Что показать в кодовом каталоге                                                                              | Требование к использованию, не blanket PASS                                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Button                    | `view`, `size`, `selected`, `disabled`, `loading`, button/link варианты; normal/action и смысловые варианты. | Не подменять навигацию button без причины. Нативная семантика, доступное имя, focus-visible; loading не должен допускать повторную операцию.      |
| Input и формы             | Label, значение, обязательность, ошибка, disabled и отправка формы.                                          | Ошибка связана с полем/формой; клавиатурная отправка и повтор после ошибки — разные состояния.                                                    |
| Dialog                    | Заголовок, содержимое, отмена/подтверждение, возврат фокуса.                                                 | Диалог не должен закрываться из-за состояния соседнего popover; destructive действие имеет явное подтверждение.                                   |
| Popup / disclosure        | Плавающий слой отдельно от раскрываемой секции в потоке.                                                     | Escape/outside click относятся к overlay-контракту, а не ко всем раскрытым секциям. Disclosure управляется заголовком и сохраняет место в потоке. |
| Toolbar / canvas controls | Активный инструмент, недоступное действие, роль GM/PLAYER, компактная компоновка.                            | Состояние определяется не одним цветом; декоративный слой не перехватывает указатель у игрового объекта.                                          |
| Panels и feedback         | Навигация разделов, pending/success/error, пустые состояния, toast.                                          | Не терять ввод/фокус при обновлении; ошибка операции должна оставаться понятной без поиска в toast.                                               |

Это небольшая система повторно используемых решений для плотного VTT, не заявка на библиотеку из сотен самостоятельных вариантов. В кейсе показывать источник, пример потребителя и границу проверки, а не число компонентов.

## Accessibility: требования и честные границы

- Проверять клавиатуру, доступные имена/labels, порядок и видимость фокуса; для icon-only действий нужен смысл без изображения.
- Проверять светлую/тёмную тему, текст на сложном фоне, масштабирование и узкую компоновку на собранной странице. Результат одной пары цветов не переносить на весь компонент.
- Передать состояние не только цветом: selected, pending, error и disabled должны быть различимы семантически и визуально.
- Уважать reduced motion и forced colors там, где они поддержаны компонентом; не объявлять на этом основании проверенным весь canvas.
- Screen reader, физический touch, IME и performance на устройствах требуют отдельной проверки. Документация их не заменяет.
- Известные провалы контраста Classic и непроверенные реальные экраны остаются видимыми в ограничениях ниже. Наличие дизайн-системы не означает, что эти долги закрыты.

## Эквивалент связи design ↔ implementation

Для этого пакета эквивалентом Figma-связки служит проверяемая цепочка: исходник токена → генератор/семантика → компонент → Storybook story → продуктовый потребитель → точечное доказательство и ограничение. Навигационные ссылки приведены в первой таблице. Паритет с Figma и доступность опубликованного Storybook не подтверждались; внешние дизайн-интеграции не использованы. Это позволяет читать кейс отдельно от закрытого дизайн-файла и не придумывать отсутствующий Code Connect.

## Предлагаемый порядок изменений

- Для нового варианта сначала проверить существующий семантический токен и компонент. Если нужен новый токен, менять исходный JSON, пересобирать производные и фиксировать изменения в одной ревизии.
- Для нового состояния добавить пример в Storybook и проверку по реальному контракту. Для слоёв отдельно пройти Escape, клавиатурный фокус, закрытие и узкую компоновку. Измерять контраст в **собранном** приложении: порядок CSS может отличаться от среды историй и тестового Vite.
- При замене примитива назвать новый путь, перечислить потребителей и сохранить переходный слой, пока они не перенесены. Снятие переходного слоя — отдельная проверка каскада и регрессий. Это предлагаемое правило contribution/change/deprecation, не утверждённая политика.

## Что проверено локально

- На чистой ревизии `cd768ba4` генератор персональных тем воспроизвёл все три закоммиченных артефакта побайтово. Это проверка генератора тем, не всего токен-пайплайна.
- На исходной ревизии прошли 28 из 31 проверок. Две статические проверки ошибочно приняли `.ability-management` за поповер: в изолированном Chromium-стенде с CSS приложения раскрытие сдвигает следующий элемент вниз на 26 px при ширинах 390 и 1050 px. Escape и внешний клик не сворачивают секцию, а Space на заголовке сворачивает её и сохраняет на нём фокус. После уточнения классификации локальный тест закрытия прошёл 4/4. Полный экран персонажа не проверен. Статический [реестр и журнал проверок](plans/uix-644-menu-inventory.md) затем сверены с ревизией: вместе с тестом закрытия прошли 12/12 проверок. Приёмка новых мест в реальных экранах остаётся открытой.
- В отдельном локальном замере UIX‑317 на собранном вебе 6 из 21 состояний кнопок современных тем не достигали 4,5:1; с локальной поправкой — 0 из 21. Classic отдельно остался ниже порога. Поправка не опубликована; этот замер не заменяет аудит доступности.
