## 1. Что показало исследование

Изучены две независимые традиции, решающие ровно эту задачу. Показательно, что
они сошлись на одном и том же ядре.

### Sync-движки (Replicache, Linear)

- Клиент записывает **намерение** — именованную мутацию с аргументами, — а не
  вычисленный результат. Мутация выполняется дважды: оптимистично на клиенте и
  авторитетно на сервере.
- У каждой мутации клиента — последовательный номер. Сервер хранит по клиенту
  «до какого номера я всё применил» (`lastMutationID`), и в ответе на pull
  сообщает его. Клиент выбрасывает подтверждённые мутации из очереди.
- При каждом обновлении с сервера выполняется **rebase, буквально как в git**:
  откатиться к последнему серверному состоянию → наложить серверный патч →
  **переиграть неподтверждённые мутации поверх** → атомарно показать
  результат.
- Ключевой момент: поскольку при rebase мутация **выполняется заново** против
  нового состояния, она может «пойти по другой ветке». Разрешение конфликтов
  выражается обычной логикой приложения, а не универсальным правилом.
- Linear делает то же самое: локальное применение, очередь транзакций,
  монотонный sync id для порядка, у транзакции есть метод отката. Их
  сооснователь формулировал прямо: sync-движок должен был появиться первым,
  иначе ничего не ощущалось бы правильно.

### Игровой netcode (client-side prediction + server reconciliation)

- Клиент немедленно применяет ввод локально той же логикой, что и сервер;
  сервер остаётся авторитетным.
- Когда приходит авторитетное состояние, клиент сравнивает его со своим
  предсказанием и при расхождении **исправляется и переигрывает все действия,
  случившиеся с того момента**.
- Отдельная практика: **сглаженная коррекция** — применять поправку сервера
  постепенно, а не мгновенным скачком, чтобы не было визуальных рывков.

### Общий вывод

Обе школы отвечают одинаково: **переигрывание неподтверждённых действий поверх
серверного состояния — это норма, а не опасность.** Безопасно оно именно
потому, что переигрывается _намерение_, вычисляемое заново, а не слепо
переприменяется старый результат.

Мой пункт «не переигрываем автоматически» был написан из верной тревоги
(молча перезаписать чужой ход) — но лечил её неверным способом: ценой потери
работы пользователя. Правильный ответ — переигрывать намерение, а логику
разрешения конфликта задавать явно для каждого типа мутации.

## 2. Что из первой редакции подтвердилось

Механика проблемы описана верно и остаётся основанием для работ.

**Быстрые действия конфликтуют по построению.** Мутация шлёт `revision`,
прочитанную из снапшота; новую ревизию клиент узнаёт только из ответа сервера.
Если оба запроса используют одну ревизию и первый уже изменил сущность,
второй получает 409. Это условный сценарий, не гарантия отказа любой быстрой
серии; применение серверного ответа в `321b86d` уже сокращает это окно.

**Цена ошибки завышена.** Сбой обрабатывается через `await load()` — полную
пересборку снапшота (20 запросов к БД) плюс перерисовку всего дерева.

> **Поправка к первой редакции.** Там было сказано «в 11 местах». Это
> завышение: из 11 вызовов `load()` только **6** — откаты при ошибке,
> остальные 5 обновляют состояние после успешной загрузки файла. Из этих 6 к
> быстрому классу относятся всего два (размер токена и правка рисунка), а
> перетаскивание токенов идёт через `runResult` и полной пересборки не
> вызывает вовсе.
>
> Значит петля «ошибка → полная пересборка» реальна, но уже, чем я описал, и
> ожидаемый эффект от этапа 1 скромнее. Механика самоконфликта ревизий
> (главная причина) от этого не меняется — она подтверждается полностью.

При разборе этих мест нашлась и содержательная ошибка: правка рисунка
перезагружала всё **именно при 409** — то есть в единственном случае, который
broadcast и так исправляет, — а прочие сбои (5xx, обрыв сети) глотала молча,
оставляя пользователя без сообщения о потерянной правке. Оба перекоса
исправлены в этапе 1.

Редакция 2 предлагала заменить CAS у быстрых сущностей по аналогии с другой
sync-моделью. Для текущего API это не безопасный вывод: локальное
переигрывание не разрешает убрать revision predicate или молча перезаписать
чужой ход. Переносим идею отдельного слоя намерений, не чужой wire protocol.

## 3. Рекомендация и граница текущей реализации

**Выбор: узкие per-entity intent overlays поверх authoritative state**, а не
общая очередь всех запросов. Независимые сущности не блокируют друг друга;
связанные записи одной сущности используют её подтверждённую ревизию.
Результат сервера важнее предсказания. Ни движение, ни conditions не получают
исключения из CAS/ACL только потому, что пользователь действует быстро.

### 3.1. Замер существующих call sites и первый срез

| Класс                                    | Фактически в `d68f8ed`                                                                                                                                | Граница рекомендации                                                                                              |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Token/bulk drag                          | `App.onBulkMove` применяет response revisions и delta через `applyBulkMoveResult`; это `321b86d`, не общая очередь drag.                              | Сначала измерить именно этот путь и порядок HTTP/broadcast; не применять delta повторно при восстановлении.       |
| Token placement                          | `OptimisticTokenMutations.place` запускает независимые запросы сразу; draft `pending:actionId`, App передаёт `placementId = actionId`.                | Сохранить отдельный transient overlay и exact-ID reconciliation, не искать дубль по координатам.                  |
| Token conditions                         | Coordinator хранит `condition + enabled`, сериализует только этот token, накладывает pending intents поверх его текущего состояния.                   | Это существующий первый intent-срез; не превращать его в универсальный протокол для движения, денег или удаления. |
| Resize / drawing PATCH                   | App применяет серверный DTO/revision; `recoverFromCanvasMutation` показывает ошибку, на 409 не вызывает полный `load`, на остальных ошибках вызывает. | Не обещать отсутствие full refetch во всех recovery paths.                                                        |
| Drawing / ruler / fog gesture            | Уже существуют локальные draft/preview в renderer; durable запись и разрешённая игроку проекция остаются серверными.                                  | Переиспользовать lifecycle draft; не прогнозировать раскрытие тумана или скрытых entities.                        |
| Dice / character sheet / world authoring | Отдельные authoritative actions; здесь нет общего spatial coordinator.                                                                                | Не предсказывать результат броска; не включать редкие содержательные правки в первый быстрый срез.                |

Проверенные entrypoints: `apps/web/src/App.tsx` (coordinator wiring,
`onBulkMove`, `onDrawingUpdate`, `submitRoll`),
`apps/web/src/optimistic-token-mutations.ts`, `canvas-bulk-move.ts`,
`use-mutation-runners.ts`, `renderers/drawing-draft.ts`.

**Наблюдаемые ограничения coordinator, не обещания будущего поведения:**

- `place()` возвращает `void`; success/error обрабатываются асинхронно через
  `acceptToken`/`onError`, draft очищается в `finally`. Это не awaitable receipt
  формы и не доказательство её lifecycle при ошибке; этот документ его не меняет.
- Conditions используют более свежий token между текущим snapshot и base.
  На первый `status === 409` выполняются `reloadToken` и одна повторная отправка
  batch; второй отказ прекращает batch. Сейчас проверяется status, не typed
  причина отказа. App создаёт новый body `actionId` на каждый `sendConditions`.
- `reloadToken` фактически читает `/api/bootstrap` и выбирает token из ответа:
  это не маленький per-token endpoint. При окончательной ошибке показывается
  сообщение, запрашивается canonical token и снимается overlay этого token;
  сбой refetch не превращается в подтверждение записи.
- Placement после snapshot-before-ack узнаётся по точному ID. App не принимает
  token response с ревизией ниже уже известной и проверяет наличие его scene.
  `reset()` инвалидирует старые callbacks через generation при смене
  campaign/membership и unmount. Это не доказательство всех ACL/scene-switch races.

### 3.2. CAS, порядок и конфликтующие broadcasts

`moveTokenSchema`, `updateTokenConditionsSchema` и bulk targets в
`packages/contracts/src/index.ts` сохраняют revision; соответствующие writers
в `apps/server/src/routes.ts` выполняют revision checks/CAS под Canvas guard.
Клиент берёт следующую ревизию из подтверждённого ответа или canonical
projection, не угадывает её и не отключает серверный predicate.

Для дальнейшего расширения задаётся такой контракт:

- Base остаётся последним разрешённым серверным состоянием; overlay не является
  заменой snapshot. Существующий `reconcileGameSnapshot` и event sequence
  остаются точками интеграции, не вводится несуществующий server `lastMutationID`.
- Чужое обновление другой сущности не ждёт нашу очередь. Обновление того же
  видимого token меняет base; **локальное** переигрывание непосланных intents
  не означает повторную HTTP-запись и не считается подтверждением.
- У conditions переигрывается «установить флаг», а не весь старый список или
  toggle; чужие несвязанные флаги сохраняются. После отказа с известной stale
  revision допустим только bounded retry по заново прочитанной разрешённой base.
  Для drag, drawing, fog и содержательных правок такое правило не подразумевается
  автоматически: conflict policy определяется отдельно для каждой команды.
- Уже отправленный request body неизменяем. Можно объединять только ещё не
  отправленные локальные intents одного совместимого жеста; подтверждённый
  effect удаляется ровно один раз. HTTP-before-broadcast и обратный порядок
  проверяются отдельно, особенно для относительного bulk delta.
- Удалённая/переставшая быть разрешённой цель не восстанавливается из старой
  base. Rebase не даёт last-write-wins права поверх чужого подтверждённого хода.

### 3.3. `actionId`: повтор транспорта не равен новому намерению

Нормативные правила для будущего retry слоя:

1. Exact retry сохраняет method/path, actor/campaign, **то же тело**, включая
   исходную revision, и тот же body `actionId`. Новый пользовательский жест
   получает новый ID. Correlation header `x-action-id` не заменяет body ID:
   `api.ts` может генерировать header отдельно.
2. Изменение payload или revision после подтверждённого отказа — новая команда,
   значит новый `actionId`. Например, conditions retry после fresh bootstrap
   не должен переиспользовать ID прежнего body. Нельзя незаметно исправить
   payload под старым ключом.
3. Timeout/обрыв после отправки — **неизвестный результат**, не доказанный отказ.
   Не создавать новый ID и не повторять относительный MOVE/создание вслепую:
   сначала восстановить canonical state и выяснить результат исходной команды.
   Exact retry допустим только для endpoint с проверенным replay-контрактом.

**Фактические server contracts неоднородны.** В `routes.ts` conditions и bulk
используют campaign-scoped `findAction` и возвращают `{ duplicate: true }`,
без сравнения полного payload и без гарантированного DTO/revision. Placement
из definition может вернуть найденный token либо тот же duplicate marker.
Поэтому текущий API нельзя описывать как универсальный hash-bound receipt
protocol; marker нельзя выдавать за полный mutation response. До обобщения
retry нужны endpoint-specific reconciliation и проверка семантики exact retry,
changed payload, actor/target scope. Это условие будущей реализации, не
исправление server handlers в данном исследовательском пуле.

### 3.4. Ошибки и rollback UX

Таблица определяет рекомендуемый контракт; различия с текущим coordinator
явно перечислены в §3.1. Универсального recovery автомата сейчас нет.

| Исход                                             | Рекомендуемое поведение                                                                                                                                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подтверждённый success                            | Применить canonical response/свежую проекцию, убрать только соответствующий overlay. Не повторять effect по второму каналу.                                                                         |
| Duplicate marker без DTO                          | Не считать marker новым состоянием; восстановить canonical projection, не выдумывать revision/координаты.                                                                                           |
| 409 stale revision / конфликт записи              | Fresh authorized base; для явно разрешённых conditions — ограниченное переигрывание флагов с новым ID. Для остальных классов показать конфликт и предложить осознанное повторение, не overwrite.    |
| 409 pause / placement-ID / другой policy conflict | Не лечить как обычный stale revision и не крутить retry loop; убрать speculative effect, показать bounded причину/текущее состояние. Текущий conditions coordinator ещё различает лишь HTTP status. |
| 401 / смена session                               | Очистить scoped pending state, сделать старые callbacks inert; продолжение возможно только в подтверждённом новом session context.                                                                  |
| 403 / недоступная цель 404                        | Убрать speculative effect; refetch безопасной проекции, не восстанавливать цель из кэша и не раскрывать причину скрытия. Нет auto replay.                                                           |
| Validation 400/422                                | Убрать speculative effect, сохранить допустимый пользовательский ввод для исправления и показать понятную ошибку. Исправленная команда получает новый ID.                                           |
| Сеть/5xx с неизвестным commit                     | Показать «результат не подтверждён», сохранить identity исходной команды для reconciliation, не обещать rollback серверной записи. Не создавать второй delta/placement.                             |
| Повторный отказ / недоступный refetch             | Остановить bounded recovery, снять неподтверждённый overlay и оставить последнюю разрешённую base либо safe waiting при утрате доступа; явно сообщить о неподтверждённом действии.                  |

Ошибка одной сущности не откатывает другие успешные действия. Визуальный
rollback — удаление локального overlay, **не** обратная серверная мутация.
Форма должна явно различать pending/success/error, но текущий `place(): void`
не даёт ей awaitable success: это ограничение runtime, а не закрытый здесь UI AC.

### 3.5. Visibility-safe replay и границы первого прохода

- Base, имена и ссылки на assets берутся только из разрешённой текущей
  проекции. Предсказание не загружает скрытые карты/токены/assets и не переносит
  GM/private данные в PLAYER DOM, accessible labels или network requests.
- Можно локально показать собственный draft и разрешённое изменение известной
  цели. Нельзя предсказывать результат dice, раскрытие fog, приватные сообщения
  или неизвестные серверные данные. Локальный fog preview не расширяет ACL.
- Перед будущим replay/retry заново проверяются контекст кампании, участник,
  цель, доступный scene и pause. Удаление цели или отзыв доступа прекращает
  pending intent; старый DTO не должен возродить её после следующего snapshot.
- Серверные role/controller/scene проверки и `campaignCanvasDatabase` остаются
  authority. Наличие client overlay, socket room или cached asset URL ничего
  не разрешает. Браузерный reset generation полезен, но не заменяет server guard.
- Расширенный журнал, offline persistence и автоматический replay после reload
  не входят в первый проход. Сглаживание допустимо лишь для уже разрешённой
  коррекции позиции; оно не должно задерживать скрытие потерявшей доступ цели.

## 4. Чего мы НЕ берём из изученного, и почему

Честная граница — иначе это превратится в переписывание всего.

- **Полноценный local-first / offline.** Replicache и Linear построены вокруг
  работы без сети: IndexedDB, устойчивая очередь, восстановление после
  перезапуска. Нам это не нужно: игра идёт онлайн в реальном времени, оффлайн
  сценария нет. Берём модель rebase, не берём офлайн-хранилище.
- **CRDT (Yjs, Automerge).** В этом срезе не проектируется совместное
  редактирование текста. Правила конкретных token intents задаются явно в §3,
  а не универсальным merge или правилом «последний победил».
- **Перевод всех мутаций в изоморфные мутаторы.** В полной модели один и тот
  же код мутации исполняется и на клиенте, и на сервере. У нас разные слои
  (Fastify + Drizzle против React), и такой рефакторинг несопоставим по цене с
  задачей. Локальное вычисление сверяется с конкретным endpoint; даже простой
  сдвиг координат не становится разрешённой записью без server CAS/ACL.
- **Замену CAS, в том числе для быстрых команд.** См. 3.2: идеи другого
  sync-протокола не ослабляют текущий authority contract.

## 6. Как проверять

Уже имеющиеся примеры (прочитаны, не запускались заново в этом docs-pool):

- `apps/web/src/optimistic-token-mutations.test.ts`: independent delayed
  placements, snapshot-before-ack по ID, reset generation, per-token conditions
  serialization, rebase без потери чужого флага, rollback отклонённых conditions;
- `apps/web/src/optimistic-token-wiring.test.ts`: структурная App wiring,
  не browser/HTTP acceptance;
- `apps/web/src/canvas-bulk-move.test.ts`: применение response revisions и
  следующий drag с обновлённой revision; это не доказательство всех сетевых гонок;
- `apps/web/src/use-mutation-runners.test.tsx`: full refetch на неизвестном
  отказе, но не на 409, и распространение ошибки вызывающему коду.

Минимальная матрица для **будущего** расширения:

1. Unit: две сущности независимы; один token сериализован; чужие несвязанные
   изменения сохраняются; sent payload неизменяем; подтверждение снимает intent
   один раз при обоих порядках HTTP/broadcast, включая относительный MOVE.
2. Real HTTP/DB: CAS без overwrite; exact replay/changed payload/actor и target
   scope проверены для конкретного endpoint, duplicate response корректно
   reconciled; rejected write не создаёт второй event/placement.
3. Failure cases: stale/pause/403/404/validation, timeout после возможного commit,
   повторный отказ и refetch failure; нет бесконечного retry или silent success.
4. Privacy/lifecycle: отзыв доступа, удаление цели, scene/campaign/session switch,
   pause и late callbacks не оживляют скрытые объекты; никакого hidden preload.
5. Browser на isolated backend: visible pending/rollback, быстрые последовательные
   и независимые действия, reconnect, GM/PLAYER; synthetic promises не заменяют
   измерение задержки или безопасность реального server contract.

Диверсия будущего нового regression test меняет проверяемое production поведение
(например, теряет response revision или пропускает rejected overlay), а не его
expected value. После восстановления повторяется тот же тест. Эти проверки и
живые latency-замеры данным Markdown не объявляются выполненными.
