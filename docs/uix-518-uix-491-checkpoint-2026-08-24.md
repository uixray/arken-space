# Чекпоинт UIX-518 / UIX-491 — 2026-08-24 (облачная сессия)

База — `8ec37be`. Ветка `claude/arken-space-env-inventory-xfp5vw`, PR #24.

## Оговорка о параллельной работе

Сессия начиналась на `5b5e742` и первым делом сделала UIX-519 и тихий fallback
`DATABASE_URL`. Пока она это делала, ровно то же самое было сделано на `main`
(`60a30a4` и `3e91327`). Дубликаты выброшены, ветка перебазирована; в ней
остаются только UIX-518 и UIX-491.

Два расхождения стоит знать, чтобы не искать их потом:

- `tsconfig.configs.json` на `main` покрывает три корневых конфига; облачный
  вариант покрывал заодно `scripts/**/*.ts`, где `measure-broadcast.ts` тоже
  вне проверки типов. **Это осталось незакрытым** — сознательно, чтобы не
  тянуть за собой отброшенный коммит.
- По `DATABASE_URL` принято решение `main`: дефолты действуют в development и
  отключены в production. Значит `pnpm dev` без экспорта переменных
  по-прежнему молча идёт на `localhost:5432`. Для `db:migrate` дыра закрыта,
  остаточный риск — только dev-сервер, и он принят осознанно.

## UIX-518 — состояние на тест, а не на прогон

### Поправка к постановке

Утверждение «все e2e работают с одной кампанией» неверно, и это меняет объём
задачи вдвое. Спеков четырнадцать, и они делятся на два класса:

- **девять** (`concept`, `world-maps`, `token-generator`,
  `canvas-token-regressions`, `story-channel`, `skill-cards`,
  `scene-workspace-dialog`, `playtest-feedback`, `inventory-input`) полностью
  мокают API через `page.route` и базы не касаются вовсе;
- **пять** (`activity-feed-layout`, `game-night`, `quick-roll-panel-resize`,
  `sidebar-button-labels`, `workspace-nav`) ходят в живой backend.

Отсюда следствие, противоречащее исходному разбору UIX-518: падения
`world-maps` и `token-generator` из второго прогона **общей кампанией не
объясняются** — это мокнутые спеки. У них другая причина.

### Решение

Из `ensureSeed` выделены `seedCampaignContent` и `createCampaignWithGmAccess`.
Фикстура `tests/e2e/campaign-fixture.ts` создаёт на каждый тест собственную
кампанию со своим GM-токеном. Живой спек берёт `test` из фикстуры, а не из
`@playwright/test`, и логинится по `gmToken`; ссылаться на
`process.env.GM_ACCESS_TOKEN` из спека больше нельзя — это снова общая
кампания.

Кампания создаётся прямо в базе: route для создания кампании нет, и заводить
его ради тестов значило бы открыть в production путь, нужный только здесь.

Попутно исправлено: `ensureSeed` выбирал «первую» кампанию через `limit(1)`
**без сортировки**. Пока кампания была одна, это не было видно; с появлением
тестовых выбор стал зависеть от плана запроса. Порядок задан явно.

Кампании после теста не удаляются: часть внешних ключей объявлена `restrict`,
и удаление зависело бы от того, что тест успел создать, — то есть падало бы
через раз ровно по той причине, которую фикстура и убирает. База под e2e
одноразовая.

### Два вынужденных отступления от документации Playwright

Оба проверены запуском, а не рассуждением:

- аргумент, отдающий фикстуру, назван `provide`, а не `use`:
  `react-hooks/rules-of-hooks` принимает вызов `use(...)` за React-хук вне
  компонента и роняет `pnpm lint`;
- первый аргумент обязан остаться деструктуризацией `{}`. На
  `async (_fixtures, …)` Playwright падает до запуска тестов, поэтому правило
  `no-empty-pattern` отключено точечно, с причиной в комментарии.

## UIX-491 — подтверждение назначения изображения токену

Вторая половина жалобы из «Сообщить»: «я не смог загрузить и назначить
картинку на токен, но при этом она назначилась». Форма сообщала только об
ошибке, а при успехе молча очищала поле файла — для человека это неотличимо от
«ничего не произошло». Блок показывается **игроку** (у мастера на его месте
«Настроить»), то есть починен ровно тот экран, с которого пришёл отчёт.

Успех называется словами и живёт до следующего действия: таймер добавил бы
гонку в тесте и шанс, что подтверждение исчезнет раньше, чем его прочитают.
Выбор другого файла снимает прежнее подтверждение. `role="status"` на
подтверждении, `role="alert"` на ошибке. Классу `.field-notice` добавлено
правило — он уже использовался в `WorldContentWorkspace`, но стиля не имел.

Тест проверен диверсией: снятие `setNotice` роняет два теста из трёх, отказ
снимать подтверждение при новом файле — третий.

### `workers: 1` больше не требование корректности

Пять живых спеков, по два повтора:

| workers | повтор 1        | повтор 2        |
| ------- | --------------- | --------------- |
| 1       | 8 passed, 1.9 м | 8 passed, 1.9 м |
| 4       | 8 passed, 48 с  | 8 passed, 48 с  |

Проверено запуском. Уточняет

| Возможность             | Статус                                                |
| ----------------------- | ----------------------------------------------------- |
| PostgreSQL              | **есть нативно**, 16.13; e2e-стенд поднимается        |
| Docker daemon           | стартует через `sudo dockerd`                         |
| Docker registry         | **403 Forbidden** на blob-запросы — образы не тянутся |
| Docker multiplayer gate | **недостижим**                                        |
| Playwright Chromium     | build **1194** при ожидаемом 1234                     |
| Playwright Firefox      | **отсутствует**                                       |
| Linear MCP              | работает                                              |

Три ловушки, которых нет на машине владельца:

1. **Фоновые процессы не переживают вызов инструмента.** Стенд надо поднимать
   и гасить внутри одного вызова.
2. **Браузер запускается только через явный `executablePath`**
   (`/opt/pw-browsers/chromium`), и `channel: "chrome"` из корневого конфига
   здесь нерабочий.
3. **Vite молча уезжает на другой порт.** Занятый 5173 не останавливает его:
   он поднимается на 5175, проверка готовности получает 200 от чужого,
   устаревшего процесса на 5173, тот умирает по ходу прогона — и шестьдесят
   тестов падают с `ERR_CONNECTION_REFUSED`, выглядя как нестабильность
   тестов. Обязателен `--strictPort` и проверка занятости порта до старта.

## Как измерять, чтобы не соврать себе

Прогоны, шедшие параллельно с `pnpm test` или `pnpm typecheck`, давали десятки
падений по всему дереву — включая публичный лендинг и мокнутые спеки. Это
голодание по процессору, а не свойство тестов. **Как данные такие прогоны
недостоверны.** Засчитывается только прогон без сторонней нагрузки; иначе
получается ровно та ложная картина, которую задача и должна была устранить.
