# UIX-516 — жизненный цикл системных строк регена

## Замер и причина

- `enduranceRegen` и `manaRegen` объявлены каноническими STAT-строками в
  стартовой раскладке и связаны с ресурсами через `RESOURCE_REGEN_STAT`.
- GM-клиент сейчас предлагает удалить любую STAT-строку, а сервер запрещает
  удаление только при ссылках из формул или каталога. На системный реген таких
  ссылок обычно нет, поэтому PATCH принимается.
- Удаление раскладки намеренно не очищает `characters.stats`. Это безопасная
  политика для обычных пользовательских строк, но здесь отдых и быстрые
  счётчики продолжают читать скрытое каноническое значение.
- `resolveStatLayout` восстанавливает только пустую или невалидную раскладку;
  валидная partial-layout без одной системной строки проходит без исправления в
  bootstrap и Socket.IO projection.
- Повторное добавление по подписи не является восстановлением: из русской
  подписи строится новый пользовательский ключ, а системная связь остаётся на
  `enduranceRegen` / `manaRegen`.
- История UIX-424 подтверждает, что обычное безопасное удаление было добавлено
  намеренно. UIX-468 убрала реген только из бросков, потому что это величина
  восстановления, а не бросаемая характеристика. Эти решения не отменяются.

## Продуктовая политика

1. Системные строки регена обязательны, находятся в видимой группе `combat` и
   имеют источник `STAT`. Их можно переименовывать, переставлять внутри группы
   и редактировать как число, но нельзя удалить, сменить источник или спрятать
   в неотрисовываемой группе.
2. Значение `0` — явное, обратимое отключение восстановления для персонажа.
   Серверный отдых уже не применяет реген `<= 0`, а быстрый счётчик уже не
   показывает кнопку восстановления; отдельная destructive-команда не нужна.
3. Старые кампании чинятся при чтении: недостающая строка возвращается с точным
   каноническим ключом, существующим значением персонажа и стартовой подписью.
   Существующая каноническая подпись сохраняется; неправильная группа/source
   исправляются. Пользовательские строки, подписи и значения не удаляются.
4. Generic `statLayoutSchema` не получает список обязательных ключей: иначе
   старая partial-layout стала бы невалидной и целиком заменилась стартовой,
   уничтожив кастомную раскладку. Нормализация выполняется после успешного
   разбора.
5. Прежний лимит в 60 пользовательских строк сохраняется: физический
   `max(62)` дополняется semantic refinement, который считает два резервных
   места только для точных системных regen-ключей в `combat`. Иначе либо
   read-repair валидной legacy-группы из 60 строк возвращал бы невалидные 62,
   либо простой `max(62)` разрешал бы 62 custom-строки и repair до 64.

## Пул 1 — доменный инвариант и сервер

- Экспортировать из `@arken/system` единый predicate/set системных regen-ключей,
  производный от `RESOURCE_REGEN_STAT`.
- В `apps/server/src/stat-layout.ts` добавить чистую нормализацию partial-layout
  и отдельный отказ `SYSTEM_STAT_ROW_REQUIRED` до проверки ссылок.
- Подключить нормализацию в `resolveStatLayout`; route продолжает сравнивать
  присланную раскладку с разрешённой проекцией и поэтому защищает старые и
  crafted-клиенты.
- Не очищать `characters.stats` и не добавлять SQL-миграцию: read-time repair
  сразу возвращает видимую поверхность, а следующая разрешённая правка
  раскладки сохранит repaired-вариант под обычной revision/CAS.
- Тесты: точный server rejection, идемпотентное восстановление missing/wrong
  group/wrong source, сохранение кастомных строк/подписей и прежнее удаление
  обычной строки; legacy-группа на прежнем лимите после repair остаётся
  валидной и повторно разрешается без потери данных.

## Пул 2 — GM editor и сквозные проекции

- В `StatLayoutCard` оставить системной строке disabled delete-контрол с
  явной подсказкой: строку нельзя удалить, для отключения нужно поставить `0`.
  `CharacterWorkspace`, `App.tsx`, `styles.css` и `ChatPanels.tsx` не менять.
- Unit: системный delete недоступен и объяснён; обычный delete по-прежнему
  вызывает `onDeleteRow`.
- HTTP/bootstrap: старая сохранённая partial-layout отдаёт обе канонические
  строки ровно один раз и сохраняет значение персонажа; crafted PATCH получает
  `409` и не меняет БД.
- Browser: GM видит восстановленные строки и disabled delete до и после reload;
  существующие проверки закрепляют `0` для отдыха и быстрых счётчиков.
- Realtime/multiplayer: GM и игроки получают одинаковую repaired layout после
  resync/reconnect; запрещённое удаление не попадает в broadcast.

## Риски и границы

- Не угадывать системный ключ по подписи и не удалять похожую пользовательскую
  строку: exact key — единственная идентичность.
- Не возвращать regen в быстрые броски и не менять формулы восстановления.
- Не трогать production-данные, `scripts/measure-broadcast.ts`, assets/stickers
  или горячие файлы параллельного агента.
