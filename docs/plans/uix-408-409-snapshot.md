# Рассылка снапшота: сузить выборку и перестать пересобирать на каждый сокет — план работ (UIX-408, UIX-409)

Исходная ревизия `31e7ff6`. Статус на `42c7ccc`: основной план реализован в
`854a637` и `5c8beaa`, измерения скорректированы в `28983b0`. Документ
сохранён как rationale; release-gates и статусы UIX-408/409 проверяются в
Linear.

Обе задачи вырастают из пункта 1 [технического разбора](../technical-review-2026-08-10.md)
и решаются в одном коде, поэтому план один. Разворачиваются они по-разному и
выкатываются отдельно: UIX-408 меняет **что** уезжает клиенту, UIX-409 — **сколько
раз это строится**.

### 1.1 Числа

Из технического разбора, измерено на боевых данных: снапшот ГМ **691 КБ**,
строится **293 мс**, около **40 запросов** к БД на сборку. Состав по размеру:
`messages` 309 КБ, `drawings` 250 КБ, `fogReveals` 138 КБ, `characters` 50 КБ,
`assets` 33 КБ. В базе 270 записей тумана и 114 рисунков на 6 сцен.

**Три поправки, без которых план будет опираться на воздух.**

1. **Состав не сходится с итогом.** 309 + 250 + 138 + 50 + 33 = 780 КБ при
   заявленных 691 КБ. Либо поля мерялись в другой момент, либо разными способами
   (сырой JSON против сжатого). Пропорции наверняка верны, абсолютные числа —
   нет. Этап 0 переснимает базовую линию одним воспроизводимым способом.
2. **«~280 запросов и ~4.8 МБ на действие» — это расчёт, а не наблюдение**, и
   сам разбор это признаёт: одна сборка умножена на семь клиентов. Расчёт
   правдоподобный, но целью приёмки может быть только измеренное число.
3. **Вызовов `broadcastSnapshots` на этой ревизии 57, а не 59**: 43 в
   `routes.ts`, 12 в `world-map-routes.ts`, 2 в `encounters.ts`. Разница не
   важна для решения, но важно, что все 57 идут через **одну** функцию
   (`routes.ts:181`), которая в соседние модули передаётся коллбэком
   (`routes.ts:622-631`). Значит UIX-409 — правка одного места, а не 57.

## 2. Часть A — туман и рисунки только для нужных сцен (UIX-408)

### 2.1 Кто на клиенте читает туман и рисунки

Проверено сплошным поиском по `apps/web/src`:

| Потребитель                  | Что читает                                     | Область                        |
| ---------------------------- | ---------------------------------------------- | ------------------------------ |
| `App.tsx:1338-1351`          | `fogReveals`, `drawings`                       | **только `activeScene`**       |
| `Orthographic2DRenderer.tsx` | приходят пропсами `activeFog`/`activeDrawings` | та же одна сцена               |
| `renderers/map-objects.ts`   | туман в контексте выбора объектов              | та же одна сцена               |
| `App.tsx:1357-1364`          | длины и максимальные `revision`                | ключ для `/api/canvas/history` |

Больше **никто**. В частности:

- **`ui/SceneManagerDialog.tsx` тумана и рисунков не читает вовсе.** Он читает
  `snapshot.scenes` и `snapshot.tokens` (`SceneManagerDialog.tsx:73-74` —
  «N токенов на сцене» для каждой сцены) и `snapshot.assets`.
- **Превью сцен нет.** Карта сцены в списке — это `<img>` на ассет
  (`SceneManagerDialog.tsx:233-239`, `App.tsx:1395-1399`), а не отрисовка канваса.
- **`WorldMapsWorkspace` тумана не читает**; он умеет только открыть сцену
  (`Sidebar.tsx:476` → `onViewScene`).

### 2.2 Поправка: игроку туман чужих сцен и так не уезжает

Разбор утверждает: «Игрок видит одну сцену; остальные пять едут к нему при
каждом действии любого участника». **По коду это не так.** SQL действительно
тянет всю кампанию, но в DTO стоит отсев:

```
fogReveals: fogRows.filter(({ fog }) => visibleSceneIds.has(fog.sceneId))   // snapshot.ts:528-529
drawings:   drawingRows.filter(({ drawing }) => visibleSceneIds.has(...))   // snapshot.ts:543-544
```

а `visibleSceneIds` для игрока — это ровно активная сцена (`snapshot.ts:342-346`).
Есть и тест, который это держит:
`tests/multiplayer/game-session.spec.ts:634-636` требует у игрока
`fogReveals` строго равным `[recoveryFog.id]`.

**Что из этого следует.** 388 КБ тумана и рисунков — это перевес **снапшота
ГМ**, а не снапшотов игроков. У игроков сужение даёт только запросы, память и
GC, но не байты по сети. Заявленный «−55% объёма» относится к одному клиенту из
семи. Экономия по-прежнему реальна — 40 запросов × 7 сокетов тянут 270 записей
тумана и 114 рисунков каждый раз, — но выигрыш по трафику меньше, чем следует
из разбора, и приёмка должна ждать разного эффекта для ГМ и для игрока.

### 2.3 Почему нельзя просто написать `where sceneId = activeSceneId`

Мастер готовит сцену, не переключая игроков:

```
// A GM may inspect and prepare another scene without moving the players.
// The server-side `active` flag remains the broadcast scene.
const [viewedSceneId, setViewedSceneId] = useState<string | null>(null);   // App.tsx:359-361
```

`viewedSceneId` ставится из трёх мест: переключателя сцен в топбаре
(`App.tsx:1435`), кнопки «Открыть для мастера» в менеджере сцен
(`SceneManagerDialog.tsx:107` → `use-scene-actions.ts:69`) и перехода со сцены
на карте мира (`Sidebar.tsx:476`). После этого `activeScene` — **не та сцена,
что активна на сервере** (`App.tsx:1249-1251`), и весь канвас, включая туман и
рисунки, рисуется по ней.

Сузив выборку до `campaign.activeSceneId`, мы получим: мастер открывает сцену 3
и видит её **без тумана и без рисунков**. Дальше он рисует туман поверх якобы
пустой сцены, а `activeCanvasVersion` (`App.tsx:1357-1364`) считается по пустым
массивам, то есть ломается и ключ подгрузки истории отмен. Ни один
существующий тест этого не поймает: тумана и рисунков нет в фикстурах
`tests/visibility.test.ts` вовсе, а мультиплеерный прогон смотрит только на
игроков после `activateScene`.

**Ответ на вопрос постановки:** да, клиент читает туман и рисунки неактивной
сцены — но **одной**, и только у мастера. Нужный набор — это
`{activeSceneId} ∪ {просматриваемая мастером}`, максимум две сцены из шести, а
не «все на всякий случай».

### 2.4 Решение: сервер должен знать просматриваемую сцену

Сервер про `viewedSceneId` не знает ничего — это локальный `useState`. Значит
клиент обязан его сообщить.

- Новое клиентское событие `scene:view` (`sceneId: string | null`) в обе карты
  событий `packages/contracts/src/index.ts` (`ClientToServerEvents:2224-2250`).
- Обработчик в `realtime.ts`: проверяет роль (`GM`) и принадлежность сцены
  кампании, кладёт в `socket.data.viewedSceneId`, отвечает **этому одному
  сокету** свежим `game:snapshot`. Это и есть «подгрузка при смене сцены»: одна
  сборка на одно осознанное действие мастера.
- `buildSnapshot(db, auth, { extraSceneIds })` — необязательный параметр.
  Умолчание — пустой набор. Выборки тумана и рисунков получают
  `inArray(fogReveals.sceneId, [...])`, **не теряя `innerJoin(scenes)`** (см. §2.6).

**`/api/bootstrap` трогать не нужно.** `viewedSceneId` — это `useState(null)` без
персистентности: после перезагрузки страницы мастер всегда возвращается на
транслируемую сцену. Проверено, добавлять параметр запроса не за чем.

Отвергнутая альтернатива — **`GET /api/scenes/:id/canvas` и подгрузка с
клиента.** Выглядит проще (не трогаем realtime-протокол), но разваливается на
первом же действии: мастер рисует на просматриваемой сцене → мутация вызывает
`broadcastSnapshots` → приходит снапшот **без** этой сцены → нарисованное
пропадает до следующего ручного запроса. Пришлось бы перезапрашивать канвас на
каждый снапшот, то есть добавить запросов вместо того чтобы убрать. Отдельный
REST-маршрут имеет смысл только как запасной путь на случай оборванного сокета
(§8).

### 2.5 Заодно — аудитория события `fog:created`

`routes.ts:3490` шлёт `fog:created` **в комнату всей кампании**, а клиент
пришивает событие к `snapshot.fogReveals` без проверки сцены
(`App.tsx:725-735`). Сегодня это безобидно: лишний туман отсеивается на
`App.tsx:1338`. После сужения — уже нет: инвариант «в снапшоте лежит туман
только видимых сцен» будет нарушаться прямо на проводе, и накопленное переживёт
любое число рассылок. Событие надо сузить тем же набором сцен, что и выборку, в
том же коммите.

Попутно: **`fog:removed` объявлен в контрактах (`index.ts:2181`) и слушается
клиентом (`App.tsx:736-748`), но сервером не отправляется никогда** — удаление
тумана идёт полной рассылкой. Мёртвая поверхность протокола;
`documentation-freshness` её не ловит, потому что смотрит только на события,
встречающиеся в `realtime.ts`. Убирать не здесь, но знать полезно.

### 2.6 Что в части A трогать нельзя

- **Токены оставить кампанийными для ГМ.** `SceneManagerDialog.tsx:73-74`
  считает «N токенов на сцене» для каждой сцены из `snapshot.tokens`. Сузим —
  тихо получим нули у всех сцен, кроме двух. Токенов нет в таблице размеров,
  выигрыш бы всё равно был мал.
- **`innerJoin(scenes)` в выборках тумана и рисунков сохранить.** У `fog_reveals`
  и `drawings` **нет колонки `campaign_id`** (`schema.ts:971-1028`) — кампания
  определяется только через сцену. Замена join'а на «отбор по списку id» снимет
  единственную проверку арендатора и превратит риск №5 техразбора из латентного
  в живой. Правильная форма: join остаётся, `inArray` добавляется.
- **Индексы уже есть**: `fog_scene_idx`, `drawings_scene_idx`
  (`schema.ts:1001`, `1027`). План запроса ухудшиться не должен, но проверить
  `EXPLAIN` на восстановленном боевом дампе стоит.

## 3. Часть B — одна сборка на рассылку вместо семи (UIX-409)

### 3.1 Точный список персонализированных полей

Это основа безопасности всего решения, поэтому список полный и с местами в
коде. Разделение на три яруса важнее, чем кажется: **ярус 1 — то, что
различается у двух игроков одной роли**, и именно на нём ломается наивное
«один снапшот на роль».

**Ярус 1. Зависит от `auth.membershipId` — различается у игрока A и игрока B.**

| Поле                                         | Чем персонализировано                                                                                                       | Где                              |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `me`                                         | Строка `memberships` самого вызывающего + его `characterId`                                                                 | `snapshot.ts:338-339`, `431-437` |
| `members`                                    | Игроку — только он сам                                                                                                      | `438-447`                        |
| `directChatContacts`                         | «Все, кроме меня» — у A и B разные списки                                                                                   | `448-453`                        |
| `characters`                                 | Игроку — только принадлежащие ему или управляемые им                                                                        | `353-362`                        |
| `characters[].controllerMembershipIds`       | Игроку список схлопывается до него самого                                                                                   | `454-463`                        |

**Итого 14 полей верхнего уровня, различающихся между двумя игроками.**

**Ярус 2. Зависит только от роли (у всех игроков одинаково).**

| Поле             | Правило                                                 | Где                    |
| ---------------- | ------------------------------------------------------- | ---------------------- |
| `scenes`         | Игроку — только активная                                | `342-345`, `465-482`   |
| `catalogEntries` | Игроку — пустой массив                                  | `483-495`              |
| `fogReveals`     | Через `visibleSceneIds`                                 | `528-542`              |
| `drawings`       | Через `visibleSceneIds`                                 | `543-555`              |
| `worldMaps`      | Черновики, `GM_ONLY`, заметки ГМ, связи неактивных сцен | `world-maps.ts:55-131` |

**Ярус 3. Одинаково для всех в кампании.**

`campaign`, `encounters`, `audio`, `audioTracks`, `snapshotVersion`,
`schemaVersion`, `buildVersion`, `buildRevision`, `serverTime` (различается на
миллисекунды, но не по личности).

> **Вывод для решения.** «Один снапшот на роль» — это утечка. Игрок A получил бы
> лист персонажа игрока B вместе с приватными заметками, его личные диалоги и
> непрочитанные, его загруженные картинки, его определения токенов и его заявки
> мастеру. Ровно то, что мультиплеерный прогон проверяет строкой
> `expect(serialized).not.toContain(note)`
> (`tests/multiplayer/game-session.spec.ts:608-610`). Формулировка пункта 2
> техразбора («строить снапшот один раз на роль») **в буквальном виде
> нереализуема**, и её нельзя брать в работу как задание.

### 3.2 Что на самом деле общее — и сколько это стоит

Из ~43 запросов на сборку кампанийными, то есть зависящими только от
`campaignId`, являются:

- `normalizeAudioTrackDeadlines` — 1 запрос + до 4 на определение длительности;
- `campaigns` — 1;
- из `Promise.all` (`snapshot.ts:71-214`) — memberships, characters,
  characterControllers, scenes, tokens+definitions, tokenControllers,
  tokenDefinitions, catalogEntries, characterCatalogEntries, fogReveals,
  drawings, assets, max(gameEvents.sequence) — **13**;
- `buildWorldMapsSnapshot` — 5;
- `listEncounters` — 1.

**Примерно 21-25 запросов из ~43, то есть около половины, не зависят от того,
кому строится снапшот.** Остальные персональные: потоки чата, курсоры чтения,
по два запроса на видимый поток (сообщения + непрочитанные), вложения,
отозванные стикеры и `listVisiblePlayerRequests` с её N+1
(`player-requests.ts:244-256` — запрос на список плюс один-два на каждую заявку).

Отдельно: `normalizeAudioTrackDeadlines` (`audio-state.ts:57-113`) — это **запись
в БД внутри пути чтения**. Сейчас при рассылке она выполняется семь раз
одновременно; CAS спасает от порчи данных, но шесть из семи попыток проваливают
`update` и уходят в дополнительный `select` (`audio-state.ts:104-109`). Одна
нормализация на рассылку — не только экономия, но и снятие гонки.

И ещё одна деталь, которая объясняет разрыв между «293 мс» и ощущением от игры:
пул к PostgreSQL — **10 соединений** (`packages/db/src/index.ts`). Семь сборок
по ~15 параллельных запросов дают около сотни запросов, конкурирующих за десять
соединений. Значит мерить надо **время всей рассылки**, а не время одной сборки:
именно очередь, а не сборка, растёт нелинейно.

### 3.3 Два варианта

**Вариант 1 — разделить сборку на общую и персональную часть, кешировать общую.**

Строим один раз общую проекцию (уже в виде DTO) и подмешиваем к ней личные поля
на каждый сокет.

- **За:** экономит и запросы, и построение DTO; делает границу персонализации
  явной в типах; открывает путь к протоколу «общая часть — широковещательно,
  личная надбавка — адресно», где сериализация тоже перестанет быть семикратной.
- **Против:** «общая часть» на поверку крошечная. По §3.1 к ярусу 3 относятся
  девять скалярных полей и два массива, а всё дорогое (`messages`, `assets`,
  `characters`) — ярус 1. `assets` вообще собирается из `visibleDefinitions` и
  `visibleCharacters`, то есть персонально по построению. Чтобы получить
  заметный выигрыш, придётся резать сущности на «общее тело» и «личный хвост»
  (`tokens` без `controllerMembershipIds` и т. д.) — а это переписывание проекции,
  где **каждая ошибка есть утечка приватности**, и проверить её можно только
  тестами, которых сейчас нет.

**Вариант 2 — кешировать дорогие общие чтения на время одной рассылки.**

`loadCampaignReadSet(db, campaignId)` читает кампанийные строки один раз;
`buildSnapshot(db, auth, readSet?)` берёт их оттуда, если дали, и читает сам,
если нет. Персонализация не меняется ни на строку.

- **За:** проекция остаётся байт в байт прежней — это проверяемо тестом
  эквивалентности (§5). Все шесть прочих вызовов `buildSnapshot` (§1.2) работают
  без правок. Диф маленький и читается целиком. Убирает ~половину запросов и всю
  семикратную нормализацию аудио. Побочно **улучшает корректность**: сегодня семь
  снапшотов одной рассылки строятся в семь разных моментов и могут расходиться
  между собой; из общего набора все семь согласованы. На это уже опирается
  проверка `new Set(resynced.map(s => s.snapshotVersion)).size === 1`
  (`game-session.spec.ts:917-919`).
- **Против:** не убирает построение DTO и сериализацию на каждый сокет. Если
  окажется, что из 293 мс большая часть — CPU, а не ожидание БД, выигрыш будет
  меньше ожидаемого.

**Берём вариант 2.**

Обоснование в трёх пунктах, по убыванию веса:

1. **Цена ошибки несимметрична.** Ошибка в варианте 2 — это неверные данные
   (заметят и починят). Ошибка в варианте 1 — это чужой лист персонажа в чужом
   браузере, и заметить её можно годами. При 14 персонализированных полях и
   нулевом покрытии «игрок A против игрока B» (§5) выбирать вариант 1 первым —
   значит делать самую опасную правку с самой слабой страховкой.
2. **Вариант 2 не закрывает дорогу варианту 1, а мостит её.** Разделение чтений
   на кампанийные и личные — это и есть первый честный черновик границы
   «общее/персональное». Когда появятся тесты из §5 и измерения из §4, вариант 1
   станет продолжением, а не переделкой.
3. **Мы не знаем, что мерить оптимизировать.** Разбивки 293 мс на «БД против
   CPU» нет ни у кого. Вариант 2 бьёт по заведомо существующей половине
   (запросы и очередь на десяти соединениях); вариант 1 бьёт по половине, размер
   которой пока предположителен. Этап 0 отвечает на этот вопрос, и если CPU
   окажется доминирующим — вариант 1 вернётся в план обоснованно.

### 3.4 Замки безопасности

Одного «мы аккуратно посмотрели» мало — нужны свойства, которые нельзя нарушить
незаметно.

| Замок                                                                                                | Что держит                                                                      |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `loadCampaignReadSet(db, campaignId: string)` **не принимает `auth`**                                | Внутри физически нечем отфильтровать по членству — проверяется одной сигнатурой |
| Набор помнит свой `campaignId`, `buildSnapshot` сверяет с `auth.campaignId` и падает при расхождении | Межкампанийное переиспользование не может произойти молча                       |
| Набор живёт только внутри одного вызова `broadcastSnapshots`                                         | Нет TTL, нет модульного состояния, нечему протухнуть между запросами            |
| Массивы набора отдаются `readonly` (и замораживаются в dev)                                          | Одна сборка не может испортить данные следующей сортировкой на месте            |
| Тест эквивалентности «с набором == без набора»                                                       | Любое расхождение проекции — красный тест, а не тихое поведение                 |
| Тест перекрёстной проекции A против B                                                                | Ловит утечку, даже если предыдущие замки обошли                                 |

Отдельно и явно: **никакого кеша по `campaignId` с временем жизни.** Соблазн
велик (семь клиентов после рестарта одновременно дёргают `/api/bootstrap`), но
кеш с TTL — это уже разделяемое состояние между запросами, у которого нет
естественной границы инвалидации и есть все шансы пережить мутацию. Если
всплеск реконнектов окажется проблемой — это отдельная задача с отдельным
разбором (§8).

Про заморозку массивов стоит сказать прямо: сегодня в `snapshot.ts` сортировка
на месте есть только по `messageRows` (`snapshot.ts:560`), а он строится
персонально (`flatMap` в строках 246-249 создаёт новый массив), так что порчи нет.
Замок нужен не от текущего кода, а от следующей правки.

## 4. Как измерять до и после

Без этого раздела план — набор намерений. Мерить надо **до** первой правки и
после каждого этапа, одним и тем же способом.

### 4.1 Где мерить

На восстановленном боевом дампе, а не на пустой базе: репетиция восстановления
уже разворачивает боевой снапшот в изолированный Compose-проект (см.
[operations.md](../operations.md)). Числа техразбора получены там же — значит
базовая линия будет сопоставима. На тестовых фикстурах туман и рисунки почти
пустые, и любое измерение покажет ноль эффекта.

### 4.2 Чем мерить

| Метрика                  | Инструмент                                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Запросов на рассылку     | Монотонный process-wide counter даёт только `PROCESS_WINDOW_ESTIMATE`; acceptance снимается отдельным изолированным процессом `scripts/measure-broadcast.ts` |
| Байт на рассылку         | `Buffer.byteLength(JSON.stringify(snapshot))` по каждому сокету, сумма                                                                                       |
| Байт по полям            | тот же `byteLength` по каждому ключу верхнего уровня — так закроется вопрос из §1.1                                                                          |
| Время одной сборки       | `performance.now()` вокруг `buildSnapshot`                                                                                                                   |
| **Время всей рассылки**  | `performance.now()` вокруг `broadcastSnapshots` — главная метрика, см. про пул в §3.2                                                                        |
| Разбивка «БД против CPU» | **N/A в текущей оснастке:** `postgres` debug вызывается до запроса и не сообщает duration. Нужна отдельная instrumentation/`pg_stat_statements`              |

Runtime-лог за флагом остаётся диагностической оценкой: конкурентная работа
процесса может увеличить query delta. Авторитетные числа снимаются только через
loopback на изолированной восстановленной копии:

```powershell
$env:ARKEN_MEASURE_CONFIRM = "isolated-copy"
$env:ARKEN_MEASURE_CAMPAIGN_ID = "<campaign uuid>"
$env:ARKEN_MEASURE_GM_VIEWED_SCENE_ID = "<inactive scene uuid>"
$env:DATABASE_URL = "postgres://...@127.0.0.1:.../..."
corepack pnpm exec tsx scripts/measure-broadcast.ts
```

Скрипт fail-closed требует нечётное число прогонов, ровно 1 GM + 6 PLAYER,
активную и отдельную просматриваемую GM сцену. Он не выбирает произвольную
кампанию и не разрешает удалённый host.

### 4.3 Таблица приёмки

Заполняется на этапе 0 и перезаполняется после этапов 3 и 6. Пустые клетки —
честно пустые: этих чисел сейчас нет ни у кого.

| Метрика (ГМ + 6 игроков, одно действие) | До  | После A | После B | Ожидание                        |

| Байт на рассылку                        |     |         |         | заметно меньше после A          |

### 5.2 Чего не хватает — и почему это критично

**1. Перекрёстная проекция двух игроков в быстром наборе. Обязательный тест.**

Единственная существующая перекрёстная проверка живёт в мультиплеерном прогоне —
Docker, полный стек, по [testing.md](../testing.md) запускается точечно при
изменениях realtime/visibility. `tests/visibility.test.ts` строит снапшот
**только для одного игрока** (`ids.player`), хотя в фикстуре с самого начала
лежат неиспользованные `ids.otherPlayer` и `ids.otherCharacter`
(`visibility.test.ts:13-18`, `84-91`).

Практическое следствие: **любая реализация «один снапшот на роль» пройдёт весь
быстрый набор зелёной.** Красным станет только Docker-прогон, который на этой
правке легко не запустить.

Тест: в одном процессе построить снапшоты для игрока A и игрока B, затем
проверить, что в снапшоте A нет ни одного идентификатора B — `characterId`,
`assetId` его загрузки, id личного диалога, тело его `GM_ONLY` сообщения,
`tokenDefinition`, где контроллер только B, его заявка мастеру, — и что
`me.id === A`. И симметрично. **Важно: строить их так же, как это делает
рассылка** (то есть из общего набора чтений после этапа 5), иначе тест докажет
что-то про `buildSnapshot`, но ничего про оптимизацию.

**2. Тест эквивалентности «с общим набором == без него».** Для каждой из трёх
ролей-персон (ГМ, A, B): результат `buildSnapshot(db, auth)` совпадает с
`buildSnapshot(db, auth, readSet)` с точностью до `serverTime`. Это и есть
формальное доказательство, что этап 6 ничего не поменял.

**3. Туман и рисунки в снапшоте — покрытия нет вообще.** В фикстурах
`visibility.test.ts` нет ни одной записи `fog_reveals` и `drawings`. Нужны:
игроку — только активная сцена; ГМ без просматриваемой — только активная; ГМ с
просматриваемой — активная плюс она; третья сцена не приезжает никому.

**4. Межкампанийная защита общего набора.** Набор, построенный для кампании 1,
при попытке применить к `auth` кампании 2 обязан бросать. Тест на бросок.

**5. Счётчик запросов как тест.** Иначе выигрыш тихо откатится первой же
правкой, добавившей чтение внутрь цикла. Порог — с запасом (§8), важна не
точность, а факт срабатывания на регрессию в разы.

**6. Ручной прогон.** Мастер переключает сцены в переключателе и в менеджере
сцен: туман и рисунки появляются; рисует на просматриваемой сцене — нарисованное
остаётся после чужого действия; отмена/повтор работают на просматриваемой сцене;
предпросмотр «глазами игрока» не показывает лишнего.

Замечания к порядку:

- **Шаг 1 до шагов 4 и 6, а не после.** Тест, написанный после оптимизации, — это
  тест, подогнанный под её поведение. Написанный до, он ловит регрессию.
- **Шаг 2 роняет `documentation-freshness`, если забыть архитектуру.**
  `tests/documentation-freshness.test.ts:97-115` вытаскивает все `socket.on(...)`
  и `emit(...)` из `realtime.ts` и требует, чтобы каждое встречалось в
  `architecture.md`. Список событий — `architecture.md:185-187`. Это не
  формальность: тест сделан именно для того, чтобы протокол не расходился с
  описанием.
- **Шаги 2 и 3 разнесены** намеренно: сервер сначала учится принимать событие и
  ничего по нему не менять, клиент только потом начинает его слать. Тогда любой
  порядок выкатки безопасен, а шаг 4 приходит на уже работающий канал.
- **Шаги 5 и 6 разнесены** по той же причине: на шаге 5 никакого нового поведения
  нет вовсе, проверяется только эквивалентность. Шаг 6 — три строки, которые
  можно откатить одним коммитом, не трогая ничего другого.
- **Меняют поведение только шаги 4 и 6.** Любое изменение поведения на шагах 0,
  1, 2, 5 — дефект, а не улучшение.

## 8. Открытые вопросы

1. **Сколько сцен держать в наборе у мастера — одну просматриваемую или
   несколько последних?** Одна проще и предсказуема, но переключение туда-обратно
   каждый раз стоит круга по сети. Кэш последних двух-трёх снял бы это ценой
   размера снапшота ГМ. Решать по замеру шага 4.
2. **Что делать, если сокет оборван, а мастер переключает сцену.** Варианты:
   показать пустой канвас до переподключения (просто, но выглядит как поломка);
   запасной `GET /api/scenes/:id/canvas` (честно, но это тот самый маршрут, от
   которого отказались в §2.4); блокировать переключатель при отсутствии связи.
3. **Порог для теста-счётчика запросов.** Точное число сделает тест хрупким,
   слишком мягкое — бесполезным. Предложение: «не больше удвоенной сборки на
   рассылку из семи сокетов», то есть ловим возврат к линейному росту, а не
   колебания в единицах.
4. **Расширять ли общий набор на всплеск `/api/bootstrap` после рестарта.** Семь
   клиентов переподключаются одновременно, каждый строит свой снапшот с нуля.
   Заманчиво, но это уже кеш между запросами со своей инвалидацией — отдельная
   задача с отдельным разбором, а не приписка к этой.
5. **Убирать ли `buildSnapshot` из проверки доступа к ассету (`routes.ts:7549`).**
   Сорок запросов на картинку — вероятно, самая дорогая строка во всём файле, но
   правка меняет модель авторизации медиа и заслуживает своего тикета.
6. **Нужен ли `scene:view` игроку.** Сейчас — нет: игрок всегда на активной
   сцене. Событие стоит с самого начала ограничить ролью ГМ, чтобы игрок не мог
   расширить свою выборку. Подтвердить, что режим «игрок смотрит другую сцену» не
   планируется.

## 9. Чего этот план не покрывает

- **Не трогает `messages` — самое большое поле снапшота** (309 КБ, 45%). До 200
  сообщений на поток уезжают заново при каждой рассылке всем семерым. Пагинация
  или инкрементальная доставка чата — отдельная задача, и по объёму она больше
  обеих здешних.
- **Не заменяет полные рассылки точечными событиями** (пункт 3 техразбора). 57
  вызовов — список кандидатов, но это дни работы и другой класс риска.
- **Не чинит N+1 в `listVisiblePlayerRequests`** (`player-requests.ts:244-256`):
  запрос на список плюс один-два на каждую заявку, и всё это персонально, то есть
  общий набор здесь не помогает.
- **Не убирает `buildSnapshot` из проверки доступа к ассетам** (§8 п. 5).
- **Не меняет протокол на «общее — широковещательно, личное — адресно».**
  Сериализация остаётся семикратной; это вариант 1 из §3.3, и он вернётся, когда
  появятся тесты и числа.
- **Не убирает мёртвый `fog:removed`** (§2.5).
- **Не делает нагрузочного тестирования.** Замеры §4 — это одна рассылка на
  боевых данных, а не поведение под одновременной игрой. Живая репетиция ГМ + 6
  (UIX-217) по-прежнему не пройдена.
- **Не проверено запуском.** План написан по чтению кода; сборка, тесты и линтер
  не запускались.

## Три вещи, которые легко пропустить и дорого чинить потом

1. **«Один снапшот на роль» нереализуем.** Четырнадцать полей верхнего уровня
   различаются у двух игроков одной роли (§3.1) — включая листы персонажей с
   приватными заметками и личные диалоги. Формулировка из техразбора взята на
   веру и в буквальном виде означает утечку.

2. **Быстрый набор тестов не поймает эту утечку.** `tests/visibility.test.ts`
   строит снапшот ровно для одного игрока, хотя второй лежит в фикстуре
   неиспользованным. Единственная перекрёстная проверка — в Docker-прогоне
   (`game-session.spec.ts:608-610`). Тест из §5.2 п.1 пишется **первым**, до
   любой оптимизации.

3. **Игроку туман чужих сцен и так не уезжает** (§2.2). Выигрыш части A по
   трафику — это снапшот ГМ, один клиент из семи; у остальных экономятся запросы
   и память, но не байты. А сузить выборку до одной активной сцены нельзя вообще:
   мастер готовит вторую сцену, и сервер о ней сегодня не знает.
