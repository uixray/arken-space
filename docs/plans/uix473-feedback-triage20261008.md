# UIX-473 — порядок разбора обратной связи

## Решение владельца — 2026-10-08

Очередь разбирается **только по прямому запросу владельца**. Автоматического
разбора перед сессиями, расписания, мониторинга и уведомлений нет.

Карта сверена с исходной карточкой UIX-473; это план сопоставления, не запись
изменения production-статусов. После доступа сверять реальные ID, дату и смысл,
не связывать отчёт только по порядковому номеру или совпадению заголовка.

## Действия при разрешённом разборе

1. Войти через отдельную операторскую авторизацию, а не прямую unrestricted DB.
2. Прочитать каждый реальный отчёт; чувствительные поля открывать только при
   необходимости, копировать только серверный redacted export.
3. Прочитанный NEW перевести в ACKNOWLEDGED. Сопоставленный отчёт связать с
   существующей задачей (LINKED); не создавать повторную карточку.
4. Для составного отчёта основной link — UIX-494, сопутствующее перекрытие
   отметить в checkpoint как UIX-467, не выдумывать поддержку нескольких links.
5. RESOLVED — только после проверки исправления конкретного сообщения на
   доступной ревизии. Старый статус Done в Linear сам по себе не такое evidence.
6. Сохранить обезличенный итог: количество рассмотренных, переходов и links,
   оставшиеся зависимости; без контактов, diagnostics, cookies и storage keys.

## Проверка / блокер

- Девять сообщений покрыты существующими задачами; новые дубли не нужны.
- Операторский local synthetic ACK/LINK проверен отдельно в UIX-318, но это не
  изменение исходных production-отчётов.
- Production-сервер остановлен владельцем. Его запуск, доступ и изменение
  реальных девяти статусов не разрешены и не выполнены. UIX-473 не закрыта.
- Следующий шаг: после отдельного разрешения проверить фактическое состояние
  исходной очереди и выполнить девять адресных переходов через операторский UI.

## Разрешённый запрос владельца — 2026-10-08, продолжение

Владелец прямо поручил разобрать девять обращений. Разрешение на этот разбор
получено; очередь по-прежнему не проверяется автоматически. По сохранённой
карте все девять тем уже имеют существующие задачи: семь различных основных
карточек, два повторных сообщения (UIX-491 и UIX-493), один сопутствующий аспект
UIX-467. Новые карточки по этой карте не требуются.

Это предварительный разбор сохранённых тем, не чтение актуальных сообщений:
реальные ID, изменения текста и текущие статусы пока недоступны. До live-сверки
нельзя объявлять сообщения решёнными или выполнять ссылки по номеру строки.
Разрешение на разбор не является разрешением самостоятельно включить сервер.
Владелец готов включить его только для конкретной подготовки деплоя, не ради
проверки очереди. Статусы и links будут обработаны в рамках этого разрешённого
запроса, когда появится разрешённый доступ; до этого блокер — доступ, а не
отсутствие поручения. Production-переходов пока нет.

## Read-only Linear сверка — 2026-10-08

Проверены UIX-473 и все семь основных карточек плюс UIX-467; это статусы
задач Linear, не статусы исходных feedback-сообщений. Текущие карточки:
Done — 491, 492, 493, 494 и сопутствующая 467; Backlog — 347, 495, 496.
Связи основной карты подтверждаются описанием UIX-473 и обратными ссылками в
карточках. В UIX-491 явно сведены оба сообщения об изображениях; UIX-493
содержит оба сообщения о прокрутке; UIX-494 связывает денежный пункт с UIX-467.

Linear-комментарии дают acceptance evidence для UIX-491 (точный browser
GM/PLAYER drag, reconnect/reload, каноническое изображение и exact-main CI) и
UIX-492 (unit/browser без restart/seek/socket mutation). UIX-494 имеет closure
комментарий с production commit и целевыми тестами, UIX-467 — scoped Chromium
layout/controls QA; для UIX-493 есть Done и PR #42 attachment, но отдельного
acceptance-комментария в проверенной карточке нет. Done этих задач не доказывает
ни чтение, ни ACK/LINK/RESOLVED исходных сообщений.

Актуальные production IDs и статусы девяти сообщений всё ещё не получены:
UIX-473 содержит историческое описание «9 NEW», а последний комментарий
подтверждает, что real production transitions не выполнены. Поэтому mapping
тем уточнён, но адресные ACK/LINK действия остаются заблокированы доступом к
реальной очереди через разрешённый операторский UI; сервер не запускался,
статусы/ссылки Linear не менялись.
