# UIX-411 — внешний мониторинг production

## Исходное состояние

- `/healthz` уже проверяет соединение с БД и возвращает `buildRevision`,
  `schemaVersion` и серверное время.
- Внешней периодической проверки и канала оповещения в репозитории нет.
- Бэкап запускается на production-хосте один раз в сутки в 03:15 со случайной
  задержкой до 15 минут. В `docs/deployment.md` указан целевой RPO 24 часа, но
  фактический успешный интервал может достигать 24 часов 15 минут, а при
  незамеченной ошибке не ограничен. Это не описано как принятый риск.

## Решение

1. Добавить GitHub Actions workflow с расписанием раз в пять минут и ручным
   запуском. GitHub-hosted runner находится вне production-хоста и не требует
   доступа к БД или секретам приложения.
2. Проверять не только HTTP 200, но и JSON-контракт: `status=ok`,
   `database=ok`, непустую ревизию, версию схемы и свежее серверное время.
3. Хранить последнее наблюдаемое состояние в одном служебном GitHub issue.
   При первом падении, восстановлении, смене ревизии или версии схемы workflow
   оставляет ровно один комментарий с упоминанием владельца; повторные
   одинаковые ошибки не создают шум.
4. Не объявлять суточный риск принятым от имени владельца. Пока отдельного
   решения нет, добавить обязательный ручной запуск штатного systemd backup
   перед каждой реальной сессией с записью snapshot ID. Строгий постоянный RPO
   и мониторинг свежести бэкапа — отдельное решение.

## Файлы

- `.github/workflows/production-monitor.yml` — внешний запуск и минимальные
  разрешения GitHub token.
- `scripts/production-monitor-core.mjs` — проверка health payload и переходы
  состояния.
- `scripts/run-production-health-monitor.mjs` — CLI проверки.
- `scripts/sync-production-monitor-issue.mjs` — дедуплицированное оповещение.
- `tests/production-monitor.test.ts` — функциональный и структурный контракт.
- `docs/operations.md`, `docs/deployment.md` — эксплуатация, канал уведомлений
  и принятое решение по RPO.

## Проверка

1. Сфокусированный Vitest-набор и обязательная диверсия.
2. `pnpm format:check && pnpm lint && pnpm typecheck && pnpm build && pnpm test`.
3. Локальная симуляция healthy / outage / recovery / revision change через
   подменённый HTTP transport; production endpoint локально не опрашивать.
4. После будущего merge — отдельный live gate: ручной workflow, временно
   неверный URL для доказательства уведомления, затем восстановление. До этого
   acceptance criterion «уведомление приходит за несколько минут» считается
   подготовленным, но не доказанным.

## Ограничения

- Production не деплоится и не опрашивается в этой ветке.
- Workflow не читает боевые данные: только публичный `/healthz`.
- Пятиминутный schedule — best effort: GitHub допускает задержку и потерю
  scheduled run. Текущий публичный репозиторий не расходует платные минуты
  standard runner; перед переводом репозитория в private нужен новый budget
  gate или другой внешний монитор.
- Изменения не затрагивают UI и параллельные файлы Claude.
