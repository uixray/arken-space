# UIX-413 — страховка изоляции кампаний

## Диагноз

- Baseline: `origin/main` `a48de5d`.
- На живом дереве маршрутов найдено 70 явно зарегистрированных путей с точным
  сегментом `:id`: 56 campaign-scoped маршрутов и 14 осознанных исключений
  (10 World Content и 4 operator feedback).
- Полный runtime-инвентарь содержит 84 параметризованных маршрута: 83 пути с
  `:id` либо именованным `:*Id` и один публичный auth-путь с `:handle`. Среди
  ID-путей 68 campaign-scoped и 15 исключений: 11 глобальных маршрутов
  канонического World Content и 4 operator-only маршрута обратной связи.
- Fastify автоматически добавляет 15 `HEAD`-алиасов к `GET`, поэтому сырой
  runtime-инвентарь содержит 99 method/path записей. Эти алиасы нельзя принимать
  за новые ручные маршруты.
- Именованные параметры вроде `:characterId`, `:membershipId` и `:postId` не
  входят в буквальный acceptance criterion задачи, но runtime-сборщик видит и
  классифицирует их: страховка не зависит от имени `id`.
- В найденных 56 маршрутах явного рабочего IDOR пока не подтверждено. Проблема
  задачи — отсутствие механического доказательства и защита от следующего
  забытого `campaignId`, а не заранее объявленная уязвимость.
- Общий composite foreign key сейчас не вводим: часть связей уже защищена
  доменными FK, а канонический World Content намеренно не принадлежит кампании.

## Решения

1. Собирать фактически зарегистрированные динамические маршруты через Fastify
   `onRoute`, а не регулярным выражением по исходникам. Так учитываются sub-router
   и программно зарегистрированные маршруты.
2. Хранить типизированный реестр политик для каждого route key `METHOD path`:
   `CAMPAIGN` либо одно из двух закрытых исключений `WORLD_CONTENT_CANON` /
   `OPERATOR_FEEDBACK`. Каждый `CAMPAIGN`-путь с точным сегментом `:id`
   дополнительно обязан иметь исполняемый foreign-entity probe; именованные
   `:*Id` в scope этой задачи получают fail-closed классификацию.
3. Сравнивать реестр и runtime-инвентарь в обе стороны. Новый незаявленный
   маршрут, исчезнувший маршрут, дубликат и устаревшее исключение должны падать.
4. Нормализовать только автоматически производные `HEAD`-алиасы. Отдельный
   `HEAD` без соответствующего `GET` остаётся самостоятельной записью.
5. Для campaign-маршрутов использовать две реальные кампании и валидный граф
   сущностей. Запрос выполняет актор кампании A с ролью, достаточной для
   same-campaign операции, а path/secondary ID принадлежат кампании B.
6. Не считать любой `403/404` доказательством. Probe обязан задавать валидный
   payload/query, точный ожидаемый отказ и контроль достижимости собственной
   сущности; для мутаций дополнительно проверяется, что foreign row не изменился.
7. Маршруты с несколькими ID получают mixed-campaign сценарий, чтобы ранняя
   валидация одного параметра не маскировала отсутствие проверки второго.
8. Файловые content-маршруты получают реальные backing files: `404` отсутствующего
   файла не должен ложно изображать tenant-защиту.
9. Производственный код меняется только при подтверждённом красным probe
   пропуске. Отдельно проверить replay ветку размещения token definition: она
   загружает токен по ID и не должна полагаться только на целостность старого
   event payload.

## Пулы

### Пул 1 — структурный контракт

1. Добавить чистые функции нормализации и сравнения route inventory.
2. Подключить `onRoute` до `registerRoutes` и зафиксировать полный непустой набор
   параметризованных маршрутов.
3. Добавить закрытые наборы глобальных исключений с русским обоснованием рядом с
   тестом и проверкой на устаревание.
4. Разнести campaign route cases по доменным модулям, не создавая монолитный
   нечитабельный файл.

### Пул 2 — двухкампанейный behavioral harness

1. Поднять мигрированную PGlite-базу, кампании A/B, GM/players и сессии.
2. Засеять минимальный валидный foreign graph для characters, scenes, tokens,
   drawings, catalog/access, stickers/assets, media, requests, encounters,
   world maps и campaign-local World Content instances.
3. Реализовать общий runner: свежий `actionId`, exact status/error, own-campaign
   control и pre/post fingerprint для мутаций.
4. Подключить к runner все campaign-scoped `:id` маршруты и классифицировать
   остальные именованные ID-маршруты тем же runtime-инвентарём.

### Пул 3 — подтверждённые исправления

1. Запустить матрицу и исправить только реально воспроизводимые пропуски.
2. Проверить duplicate-action replay для
   `POST /api/token-definitions/:id/placements`; при подтверждении добавить
   campaign-scoped lookup и регрессию.
3. Не расширять задачу миграциями или RLS без отдельного решения.

### Пул 4 — доказательства и документация

1. Обновить `docs/architecture.md` и `docs/testing.md`: приложение остаётся
   источником tenant predicates, но их полнота теперь контролируется реестром и
   behavioral matrix.
2. Провести структурную диверсию: временно зарегистрировать
   `/api/__uix413_diversion/:id` и получить точный `UNLISTED_ID_ROUTE` для
   ручного `GET`; автоматически производный `HEAD` должен быть распознан по
   Fastify metadata и не дублировать ошибку.
3. Провести behavioral-диверсию: временно убрать campaign predicate у
   `PATCH /api/scenes/:id`; должен упасть именно scene isolation case, а foreign
   scene должна измениться только в намеренно сломанной версии.
4. Восстановить код и получить зелёные focused tests, затем полный gate.

## Гейты

```text
pnpm format:check && pnpm lint && pnpm typecheck && pnpm build && pnpm test
pnpm test:multiplayer
```

- `build` выполняется перед `test` на чистом checkout.
- `test:multiplayer` обязателен из-за изменения access/tenant страховки. Он
  запускается без конвейера, с проверкой реального exit code и очисткой только
  созданного этим прогоном Docker-окружения.
- `test:e2e` не является issue-level гейтом: UI-поток не меняется. Будущий PR
  всё равно получит отдельный GitHub Actions e2e workflow.
- Локальная готовность не означает push, PR, merge или production deploy.

## Риски

- Ранний `400`, role-based `403`, missing file `404` или replay-ответ могут
  замаскировать забытый tenant predicate. Поэтому нужны валидные payload,
  same-campaign controls и postconditions.
- Общая mutable fixture способна связать независимые мутации. Сущности для
  разрушительных probes должны быть уникальными либо пересоздаваться.
- Произвольное текстовое исключение превратит реестр в лазейку. Допустимы только
  два именованных и точно перечисленных глобальных набора.
- Работа идёт локально в `codex/uix-413-campaign-isolation`; чужие ветки,
  незакоммиченные файлы основного checkout и production не затрагиваются.
