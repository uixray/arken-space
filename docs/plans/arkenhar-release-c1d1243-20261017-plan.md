## Этапы

Каждый этап — отдельный скрипт в новой приватной папке
`/opt/arken-space/releases/release-c1d1243f-20261017/` (root, `umask 077`),
fail-closed, с receipt JSON. Любой FAIL — остановка и отчёт, не обход.

### 0. Сборка образов вне ноутбука (GitHub Actions)

- Новый `workflow_dispatch`-workflow `release-images.yml`: вход — 40-символьный
  SHA, проверка, что он входит в `origin/main`; `docker build` по
  `Dockerfile.server` и `Dockerfile.web` на `ubuntu-latest` (amd64);
  `docker save` в один tar; `manifest.json` с SHA, image ID, sha256 и размером
  архива; artifact с `retention-days: 1`. Секретов в образах нет (Dockerfile без
  секретных ARG, env подаётся в рантайме).
- Workflow меняет только `.github/` → отдельный PR, merge **по разрешению
  владельца**. Сборка всё равно берёт ровно c1d1243, а не HEAD main.
- Доставка: на ноутбуке `gh api …/artifacts/<id>/zip` отдаёт короткоживущую
  подписанную ссылку; хост скачивает по ней `curl` — токен GitHub на хост не
  попадает. Запасной путь: скачать на ноутбук и `scp` (медленнее).
- На хосте: `sha256sum` архива = manifest, `docker load`, image ID = manifest.
  Теги `arken-release-server:<sha>` и `arken-release-web:<sha>`.

Почему не на хосте: сборка pnpm-монорепо съест RAM/CPU живого сервиса, а
build cache — несколько ГБ из 8 свободных при требовании `MIN_FREE + 5 GiB`.

Репо публичный: artifact сутки виден залогиненным пользователям GitHub. Внутри
только публичный код — приемлемо, но решение за владельцем.

### 1. Свежий снимок и rollback-идентичность (прод не меняется, кроме паузы API ~2–3 мин)

### 2. Репетиция восстановления + миграций на одноразовом контуре (прод не меняется)

Отдельный Compose-проект `arken-restore-c1d1243f`, только loopback,
собственный том PostgreSQL и временная папка медиа:

1. `restic restore <snapshotId>` во временную папку; сверка checksum дампа и
   медиа с manifest снимка.
2. Восстановление дампа в одноразовый PostgreSQL (тот же образ `742f40ea…`),
   сверка счётчиков таблиц с `database-counts` снимка.
3. Старт **кандидата c1d1243** на этой копии → сервер сам применяет
   0060/0061 к реальным данным. Ожидание: healthz `c1d1243`, schemaVersion 62,
   ledger `62|1792075085745`, счётчики таблиц не изменились, 3 старых штампа
   читаются.
4. Receipt `rehearsal-receipt.json` (снимок, checksums, counts до/после,
   ledger, image ID, cleanup). Формат — по смыслу `runner.json` schema 2, но
   это **не** вывод `restore-rehearsal` раннера; так и пишем в отчёте.

### 3. Медиа-проверка на том же одноразовом контуре

Через SSH-туннель на loopback-порт контура: вход тестовым аккаунтом, созданным
только в копии, загрузка одной картинки и одного аудиофайла в копию кампании,
проверка отдачи. Затем `docker compose -p arken-restore-c1d1243f down -v`
(только именованный том этого проекта), удаление временных папок, проверка, что
контейнеров/томов/портов проекта не осталось. В живой кампании ничего не
загружается.
