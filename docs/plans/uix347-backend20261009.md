# UIX-347 terrain stamps — backend-first pool (2026-10-09)

## Scope and contract

This pool extends legacy `drawings` rows with a backwards-compatible `kind` discriminator. Existing/missing values are `FREEHAND`; `STAMP` stores the fixed `builtin-terrain-v1` pack key, whitelisted asset key, size, rotation, and `PUBLIC`/`GM` layer. Each placed object keeps its own database UUID, author membership, coordinates, and revision. Uploaded packs, arbitrary URLs/paths, multi-place/batch authoring, and client-supplied identity/revision are not supported.

The only catalogued prototype assets are the owner-requested generated `forest`, `mountains`, and `clouds` PNGs. Exact copies live under `apps/server/assets/terrain-stamps/` and are not in the web public directory. Docker's existing `COPY apps/server apps/server` includes them; `../assets/terrain-stamps` resolves from both source and bundled `apps/server/dist/index.js` locations.

## Authorization and visibility

- Stamp creation, transform/layer changes, copy, delete, bulk operations involving any stamp, and undo/redo of stamp actions are GM-only, even for `PUBLIC` stamps or the creating membership.
- A player snapshot contains only `PUBLIC` stamps from the same scenes as the existing drawing projection. `GM` rows are filtered before DTO construction, so their ids, coordinates, author, asset key, and transform are not serialized.
- Built-in asset bytes are served only from a fixed key-to-file map. Catalog enumeration is GM-only. Asset reads require session auth; a player may read an asset only when that exact campaign has a `PUBLIC` instance in its active scene. Foreign campaigns and hidden-only assets return 404; anonymous requests return 401. Responses are private/no-store and authorization precedes response validators/ranges.
- **Visibility intentionally follows existing drawing semantics, not token fog rules:** public stamps in the active scene remain in the drawing snapshot and authorize their raster even if a fog overlay covers the coordinates. Fog-based concealment for drawings/stamps is not implemented or claimed by this pool.
- Public stamp actions are GM-authored and do not appear in a player's personal history. Compound history containing any stamp receives GM scope. Hidden before *or* after states retain GM scope, preventing a GM-layer transition from exposing historical metadata.

## Persistence and migration

`0048_sour_ultimatum.sql` adds `kind` with `FREEHAND` default and nullable stamp-only columns guarded by checks. The STAMP check explicitly tests every metadata column for non-null in addition to whitelist/range constraints. Existing drawing operations retain their legacy author-or-GM behavior. Stamp operation state is recorded in existing `game_events`/`action_journal` transactions so object metadata participates in stale-revision checks, copy, bulk, undo, and redo without a parallel history store.

## Boundaries still open

No frontend integration is implied by backend contract alone. There is no upload/pack-management API, no campaign-specific asset replacement, no production art approval or licensing claim, and no fog-aware drawing visibility. The owner must decide whether the three generated assets become an approved shipped pack and whether future public stamps should honor fog occlusion.
