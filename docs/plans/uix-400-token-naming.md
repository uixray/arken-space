# Переименование персонажа не меняет имя токена — план работ (UIX-400)

Ревизия `77e58a1`. Статус: план к утверждению, реализация не начата.

Задача с игры 09.08: персонажа переименовали с «Хорист» на «Тейн», подпись под
токеном осталась старой. Симптом воспроизводится по коду однозначно — ни один
маршрут не связывает `characters.name` с именем токена. Но чинить это «в лоб»
нельзя: у одного персонажа осмысленно бывает несколько токенов с разными
именами, и любая автоматическая правка обязана уметь их различать.

Этот план выбирает **один** способ из трёх и объясняет, почему остальные два
отвергнуты; отдельно закрывает уже разошедшиеся имена в боевых данных.

### 1.1 Имён три, а не два — и одно из них уже производное

> **Поправка к постановке.** В задаче названо одно самостоятельное поле,
> `tokenDefinitions.name`. Полей с именем в этой цепочке **три**:
> `characters.name`, `tokenDefinitions.name` и `tokens.name`.

И это важно, потому что **одно звено уже сделано производным**. В проекции
снапшота (`snapshot.ts:496-504`):

```
tokens: visibleTokens.map(({ token, definition }) => {
  const { updatedAt: _updatedAt, ...dto } = token;
  return {
    ...dto,                    // сюда попадает token.name
    ...
    name: definition.name,     // и тут же затирается
```

`token.name` раскладывается в DTO и немедленно перезаписывается именем
определения. Проверено сплошным поиском по `apps/`, `packages/`, `tests/`:
`tokens.name` на сервере **только пишется** — при размещении (`routes.ts:2828`)
и при восстановлении холста из журнала (`routes.ts:4295`, `4331`, `4515`). Ни
одно чтение этого столбца не доходит до клиента. Всё, что на клиенте зовётся
`token.name` (`TokenDto.name`, `packages/contracts/src/index.ts:1758`), — это
имя определения.

Из этого следуют два вывода, на которых стоит весь план:

1. **Разорвана ровно одна связь: персонаж → определение.** Связь
   определение → размещение уже вычисляемая. Значит задача — не «протянуть имя
   через три таблицы», а «сделать вторым производным ещё одно звено, тем же
   приёмом, что уже применён».
2. **Правка `PATCH /api/token-definitions/:id` (`routes.ts:3268-3282`) не
   трогает `tokens.name` — и это не дефект.** Переименовали определение,
   строки `tokens` остались со старым именем, но никто их не читает. Чинить
   нечего; трогать — значит добавлять запись без потребителя.

### 1.2 Как имя попадает в определение

Ровно два входа, и оба копируют строку один раз:

- **«Добавить токен в центр»** (`SetupPanel.tsx:408-413`). Клиент собирает
  запрос в `token-placement.ts:59-72` и кладёт `name: character.name`. Сервер
  (`routes.ts:2530-2539`) создаёт определение с этим именем. Схема запроса
  требует непустое имя (`contracts/src/index.ts:646`).
- **Палитра токенов**, диалог «Новый токен» (`TokenPalette.tsx:283-339`). ГМ
  вводит имя руками, персонажа выбирает отдельным полем. Пустое имя не
  принимается — ни клиентом (`TokenPalette.tsx:285`), ни схемой
  (`contracts/src/index.ts:752`).

После этого имя определения живёт своей жизнью. Переименование персонажа
(`routes.ts:1339-1363`) обновляет одну строку `characters` и пишет
`character.updated` в `game_events` — и всё.

### 1.3 Несколько токенов у одного персонажа: поддержано, но наполовину

Предпосылка задачи верна, но с оговоркой, которая влияет на выбор варианта:

- **Ограничения «один персонаж — одно определение» нет.** У
  `token_definitions` единственный индекс — по кампании (`schema.ts:906`).
  Создать «Тейн», «Тейн верхом» и «Тейн в форме зверя» с одним `characterId`
  палитра позволяет.
- **Но путь «от персонажа» знает только про первое.**
  `characterTokenPlacementRequest` (`token-placement.ts:49-51`) берёт
  `.find((item) => item.characterId === characterId)` — первое совпадение в
  массиве снапшота. Порядок в снапшоте ничем не задан
  (`snapshot.ts:393-399` — фильтр без `orderBy`). То есть кнопка «Добавить
  токен в центр» у персонажа с тремя формами кладёт на стол произвольную из
  них.
- Все три при этом достижимы из лотка над картой (`App.tsx:2560-2601`) и из
  палитры — там перечисляются определения, а не персонажи.

Отсюда: **различие «своё имя» / «имя персонажа» реально существует в
пользовательском сценарии, и его нужно уметь хранить, а не угадывать.**

### 1.4 Три места, где связь с персонажем рвётся

Любое правило «токен без своего имени зовётся как персонаж» обязано ответить,
что происходит, когда персонажа больше нет:

| Событие                       | Где                                          | Что делает                                                      |
| ----------------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| Архивация персонажа           | `routes.ts:1511-1522`                        | `token_definitions.character_id := null` у всех его определений |
| Смена персонажа у определения | `routes.ts:3253-3266`, `3268-3282`           | `characterId` можно переставить или обнулить через PATCH        |
| Удаление строки персонажа     | `schema.ts:889-891` — `onDelete: "set null"` | Маршрута нет; путь один — операторский сброс                    |

Про последнее: GM-маршрута `DELETE /api/characters/:id` в проекте нет
(проверено), удаление персонажей делает только операторский сброс,
`scripts/gameplay-reset-core.mjs`, и он удаляет `token_definitions` (строка 65)
**до** `characters` (строка 66). Порядок закреплён `tests/reset-cli.test.ts`.
Это существенно для §3.1.

## 2. Три варианта и почему выбран один

### 2.1 Вариант A — производное отображение

Токен без собственного имени показывает имя персонажа.

Чтобы этот вариант вообще существовал, в данных должно быть различимо «имени
нет» и «имя есть, но совпадает с персонажем». Сегодня `tokenDefinitions.name`
— `notNull`, и оба входа (§1.2) его всегда заполняют, так что различия нет.
Значит вариант требует схемного изменения: `name` становится nullable, а
`NULL` означает «зовусь как мой персонаж».

Плюсы: единственный вариант, где намеренное имя («Тейн верхом») и
следование за персонажем — разные состояния данных, а не догадка. Переименование
персонажа не пишет ни строки. Согласуется с тем, как уже устроено звено
определение → размещение (§1.1).

Минусы: миграция, `CHECK`-ограничение, три места отвязки (§1.4) и новое поле в
DTO для редактора.

### 2.2 Вариант B — переименование персонажа переименовывает токены

`UPDATE token_definitions SET name = $new WHERE character_id = $id`.

Дёшево и укладывается в существующую транзакцию `PATCH /api/characters/:id`.
Но безусловно затирает «Тейн верхом» и «Тейн в форме зверя» — то есть ровно тот
сценарий, ради которого поле сделано самостоятельным. Отвергнут.

Сузить его до «только тех, что совпадали» — это уже вариант C.

### 2.3 Вариант C — обновлять только совпавшее имя

`... WHERE character_id = $id AND name = $old`.

Ломается тихо и предсказуемо:

- ГМ переименовал персонажа дважды подряд, между переименованиями страница не
  успела получить снапшот: `$old` во втором запросе — уже не то, что в базе,
  правило не срабатывает, и никто не узнает;
- токен намеренно назван так же, как персонаж («Тейн» — основная форма, «Тейн
  верхом» — вторая): первый переименуется, второй нет, и через две сессии
  никто не вспомнит, почему;
- регистр, неразрывный пробел, `trim` в схеме (`contracts/src/index.ts:773`) —
  каждая мелочь превращается в «иногда работает».

Главное же: сравнение строк — это попытка **восстановить утраченное
намерение**. Намерение можно просто хранить. Отвергнут как постоянное правило;
однократно, при разборе боевых данных, сравнение строк применимо — см. §4.

### 2.4 Решение

**Вариант A.** Обоснование, по убыванию веса:

1. **Он единственный не угадывает.** B и C принимают решение за ГМ; A даёт ГМ
   его выразить и запоминает.
2. **Это не новый приём, а второй экземпляр существующего.** Имя размещённого
   токена уже вычисляется из определения (`snapshot.ts:504`). Мы добавляем ту
   же ступень выше: имя определения вычисляется из персонажа, если своего нет.
   Проекция остаётся единственным местом, где имя «собирается».
3. **Переименование персонажа перестаёт быть операцией записи по связанным
   таблицам.** В B каждое переименование — это `UPDATE` по неизвестному заранее
   числу строк внутри транзакции, которая сегодня трогает ровно одну.
4. **Существующие расхождения чинятся один раз и под присмотром** (§4), а не
   размазываются по рантайм-эвристике.

Цена честно: миграция, `CHECK`, три места отвязки и одно новое поле DTO. §3
разбирает каждое.

## 3. Что меняется

### 3.1 Данные — миграция `0036`

```sql
alter table token_definitions alter column name drop not null;
alter table token_definitions
  add constraint token_definitions_name_or_character_check
  check (name is not null or character_id is not null);
```

**Данные не трогаются.** Ни одна существующая строка не обнуляется — иначе мы
молча потеряем намеренные имена. Разбор расхождений — §4.

Ограничение читается так: «безымянное определение обязано за кем-то следовать».
Оно же превращает каждое место отвязки (§1.4) в ошибку на уровне БД, если его
забыли доработать, — то есть в падающий тест, а не в тихую строку с пустым
именем на боевом столе.

Про операторский сброс: `token_definitions` удаляются раньше `characters`
(`scripts/gameplay-reset-core.mjs:65-66`), поэтому `onDelete: "set null"` по
FK на персонажа при сбросе не срабатывает и ограничение не нарушается. Порядок
закреплён `tests/reset-cli.test.ts` — его достаточно, менять сброс не нужно.
**Но в план приёмки прогон сброса войти обязан**: это единственный путь, где
строки `characters` удаляются физически.

Требования `tests/migration-integrity.test.ts` к новой миграции: запись в
`meta/_journal.json` с `idx: 36` и файл `meta/0036_snapshot.json`. Оба проверки
падают на коммите, если что-то забыто (`migration-integrity.test.ts:60-136`).
Миграция DDL-ная, так что `drizzle-kit generate` её сгенерирует; `CHECK` в
`schema.ts` объявляется через `check()` — приём уже используется, например
`schema.ts:876-879`.

### 3.2 Контракты

`packages/contracts/src/index.ts`:

- `createTokenDefinitionSchema.name` (`:752`) → `.nullable().default(null)` плюс
  `superRefine`: `name !== null || characterId !== null`;
- `tokenDefinitionUpdateSchema.name` (`:762`) → `.nullable().optional()`;
- `createTokenSchema.name` (`:646`) → `.nullable().optional()` с тем же
  условием относительно `characterId`;
- **`TokenDefinitionDto` (`:1672-1683`) получает два поля вместо одного:**

  ```
  name: string;          // разрешённое имя, только для показа
  ownName: string | null; // собственное имя; null = «зовусь как персонаж»
  ```

  Без второго поля редактор в палитре не может отличить «ГМ написал ‘Тейн’» от
  «имя пришло от персонажа», и любое сохранение формы превратит следование в
  жёсткую копию — то есть вернёт ровно ту ошибку, ради которой всё затевается.
  `TokenDto` (`:1749-1772`) остаётся с одним `name`: карта показывает, но не
  редактирует.

### 3.3 Сервер

**Разрешение имени — одно чистое место.** Новый модуль
`apps/server/src/token-name.ts`:

```
resolveTokenName({ definitionName, characterName }) -> string
```

Правило: `definitionName ?? characterName ?? "Без имени"`. Третья ветка при
валидных данных недостижима (ограничение из §3.1 плюс FK гарантируют, что при
`name = null` персонаж есть), но остаётся как защита от битой строки: пустая
подпись на карте хуже, чем «Без имени».

Отдельная функция, а не тернарник в проекции, — по устоявшемуся в проекте
приёму: `renderers/fog.ts`, `renderers/camera-fit.ts`, `ui/asset-picker-logic.ts`
вынесены ровно затем, чтобы решение проверялось тестом, а не только глазами.

**`snapshot.ts`:**

- собрать `Map<characterId, name>` по **всем** `characterRows`, а не по
  `visibleCharacters` (`snapshot.ts:352-362`). Игрок может управлять токеном
  персонажа, чей лист ему не виден; если брать отфильтрованный список, у него
  подпись станет «Без имени»;
- `tokens[].name` (`:504`) → `resolveTokenName(...)`;
- `tokenDefinitions[].name` (`:519`) → то же; рядом добавить `ownName:
definition.name`.

> **О видимости.** Раньше ГМ мог переименовать персонажа так, что подпись
> токена оставалась прежней, — по недосмотру, но иногда это выручало. После
> правки подпись пойдёт за именем. Инструмент для «токен зовётся не как
> персонаж» никуда не девается — это и есть собственное имя. Новой утечки нет:
> сегодня подпись и так равна имени персонажа на момент создания.

**`routes.ts`, три места отвязки:**

| Место                                           | Что добавить                                                                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Архивация, `1511-1522`                          | Перед обнулением `character_id` материализовать имя: `set name = coalesce(name, <имя персонажа>), character_id = null` |
| `PATCH /api/token-definitions/:id`, `3253-3282` | Если после применения патча `characterId === null && name === null` → `400 TOKEN_NAME_REQUIRED`                        |
| Размещение, `2828`                              | `tokens.name` остаётся `notNull`; писать туда разрешённое имя, а не `lockedDefinition.name`                            |

Архивация материализует молча — она и так пакетная операция без формы, спросить
некого. PATCH отвечает ошибкой — это диалог, ГМ на месте, и молчаливое
«сохранили какое-то имя» здесь хуже явного «введите имя».

Восстановление холста (`routes.ts:4295`, `4331`, `4515`) не трогаем: оно
переписывает `tokens.name` из JSON-снимка строки, поле мёртвое для показа, и
любая правка тут — риск ради нуля.

**`POST /api/tokens` (`2530-2539`):** `name: body.characterId ? null : body.name`.

### 3.4 Клиент

- **`token-placement.ts:59-72`** — перестать посылать `name: character.name`.
  Это одна строка и первопричина всей задачи.
- **`TokenPalette.tsx`, форма (`283-339`):**
  - поле «Название» перестаёт быть обязательным, **когда выбран персонаж**;
    подсказка под полем: «Пусто — токен называется по персонажу»;
  - при открытии существующего определения в поле кладётся `ownName`, а не
    `name` (`TokenPalette.tsx:265`), иначе первое же сохранение зафиксирует
    производное имя как собственное;
  - в теле запроса `name: trimmed || null`;
  - проверка `if (!name.trim()) return setError(...)` (`:285`) остаётся, но
    только для определений без персонажа.
- **`TokenPalette.tsx`, карточка (`92-98`):** если `ownName !== null` и
  связанный персонаж есть и `ownName !== character.name` — маркер расхождения и
  кнопка «Назвать по персонажу» (шлёт `name: null`). Это единственная
  видимая точка починки старых расхождений (§4).
- Остальные места показа (`Orthographic2DRenderer.tsx:1732-1737`, `2522-2530`,
  `2533-2549`, `2780`, `App.tsx:2598-2600`) читают `name` из DTO и **не
  меняются вовсе**. В этом смысл того, что имя собирается на сервере.

## 4. Уже разошедшиеся имена в боевых данных

Механизм из §3 чинит будущее. Сегодняшний «Хорист» на столе он не тронет:
у определения есть собственное имя, и с точки зрения новой модели оно
намеренное.

Автоматически обнулить всё подряд (`SET name = NULL WHERE character_id IS NOT
NULL`) нельзя — потеряем «Тейн верхом». Обнулить совпавшие — бессмысленно:
совпавшие как раз не сломаны. Значит решение принимает ГМ, а план обязан
сделать это дешёвым и заметным.

**Этап 0 — измерить, до всякого кода.** Запрос только на чтение:

```sql
select d.id, d.name as token_name, c.name as character_name
from token_definitions d
join characters c on c.id = d.character_id
where d.name is distinct from c.name
order by c.name;
```

Число строк решает, нужен ли отдельный инструмент. Кампания одна, персонажей
единицы — ожидание порядка десятка строк, и тогда достаточно маркера в палитре
(§3.4) и одного прохода ГМ руками. Если строк окажется много, вернёмся к
вопросу отдельным решением; выносить его в план вслепую — гадание.

**Что показывать ГМ.** Маркер на карточке в палитре («Персонаж: Тейн, токен:
Хорист») и одна кнопка. Не диалог, не мастер миграции: расхождение — это
нормальное состояние для «Тейн верхом», и интерфейс не должен требовать его
устранить.

## 6. Что тестом, что руками

**Юнит (vitest, node) — `token-name.test.ts`:** своё имя побеждает имя
персонажа; `null` + персонаж → имя персонажа; `null` без персонажа → «Без
имени»; пустая строка (не `null`) остаётся пустой строкой — это состояние
данных, которое схема не должна была допустить, и подменять его молча нельзя.

**Юнит — `token-placement.test.ts`** (файл есть): запрос на создание токена
персонажа больше не содержит `name`.

**Интеграционные (сервер, поверх существующих в `tests/`):**

- переименовали персонажа → в снапшоте и `tokens[].name`, и
  `tokenDefinitions[].name` новые, ревизия определения **не изменилась**;
- у определения своё имя → переименование персонажа его не трогает;
- архивация персонажа → у определения появилось материализованное имя,
  `character_id` пуст, `CHECK` не нарушен;
- `PATCH` с `characterId: null` у безымянного определения → `400
TOKEN_NAME_REQUIRED`, ревизия не выросла;
- `POST /api/token-definitions` без имени и без персонажа → `400` на уровне
  схемы;
- игрок-контроллер токена, чей лист персонажа ему не виден, получает в снапшоте
  имя, а не «Без имени» (регрессия на `visibleCharacters` из §3.3);
- прогон `scripts/gameplay-reset-core.mjs` в изолированной базе с
  безымянным определением — сброс проходит, `CHECK` не срабатывает.

**Component (vitest, jsdom) — палитра:**

- открытие определения с производным именем кладёт в поле пустую строку, а не
  имя персонажа;
- сохранение с пустым полем при выбранном персонаже шлёт `name: null`;
- маркер расхождения появляется только при `ownName !== null && ownName !==
character.name`;
- «Назвать по персонажу» шлёт `name: null` и текущую ревизию.

**E2E:** ГМ переименовывает персонажа в листе → подпись под токеном на карте и
в списке «Объекты карты» меняется без перезагрузки (снапшот рассылается,
`routes.ts:1366`).

**Руками:** токен без картинки (инициалы, `Orthographic2DRenderer.tsx:2523`) —
инициалы тоже должны поменяться; токен в стопке (`:1736`, `:2538`) — суффикс
«+N» не съел имя; длинное имя персонажа (60+ символов) — подпись под токеном не
ломает раскладку; глазами игрока (`/api/preview/:membershipId`).

## 8. Что уточнить у пользователя

Каждый вопрос сформулирован так, чтобы ответить одной строкой.

1. **Правильно ли, что у персонажа бывает несколько токенов с разными именами
   («Тейн», «Тейн верхом»)?** — да / нет. Если «нет», выигрывает вариант B из
   §2.2, и план сокращается втрое.
2. **Что сделать с «Хористом» и другими сегодняшними расхождениями: свести к
   именам персонажей или оставить как есть и править по одному?** — свести /
   по одному.
3. **Пустое поле «Название» как способ сказать «зовусь по персонажу» — понятно,
   или нужен отдельный переключатель «называть по персонажу»?** — понятно /
   нужен переключатель.
4. **Должна ли подпись под токеном совпадать с именем персонажа для игроков,
   которым этот персонаж не виден?** — да / нет. От ответа зависит, брать в
   §3.3 все строки персонажей или только видимые.

## 9. Чего этот план не покрывает

- **Не удаляет `tokens.name`.** Столбец остаётся: его пишет восстановление
  холста, а `before`/`after` в `action_journal` (`schema.ts:1990-1991`) — это
  JSON-снимки целой строки, и снос столбца потребовал бы обращаться с уже
  записанной историей. Отдельная задача с собственной ценой.
- **Не чинит выбор определения в `characterTokenPlacementRequest`**
  (`token-placement.ts:49-51`, §1.3): у персонажа с тремя формами кнопка
  «Добавить токен в центр» по-прежнему кладёт произвольную. Задача смежная и
  заметная, но это выбор сущности, а не имя.
- **Не трогает имена сцен, персонажей, файлов и карт мира** — там своя логика
  и свои маршруты.
- **Не вводит уникальность имён.** Два токена «Тейн» останутся допустимы.
- **Не переносит блок «Токены» из палитры куда-либо** — размещение
  интерфейса не в этой задаче.
- **Не проверено запуском.** План написан по чтению кода на ревизии `77e58a1`;
  сборка, тесты и линтер не запускались. Числа расхождений из §4 предстоит
  снять на этапе 0.

## Три вещи, которые легко пропустить и дорого чинить потом

1. **`tokens.name` уже мёртв для показа** (§1.1). Кто-то, читая задачу как
   «протянуть имя по трём таблицам», напишет `UPDATE tokens` и добавит запись,
   которую никто не читает, — и решит, что починил.

2. **Архивация персонажа обнуляет `character_id` у определений**
   (`routes.ts:1511-1522`). Без материализации имени безымянное определение
   останется висеть ни на чём. `CHECK` из §3.1 — единственное, что превращает
   это из тихой пустой подписи в громкую ошибку.

3. **В форму редактора нужно класть `ownName`, а не `name`.** Иначе первый же
   ГМ, открывший токен, чтобы поменять картинку, и нажавший «Сохранить»,
   зафиксирует текущее имя персонажа как собственное — и следующий rename снова
   «не сработает». Ошибка невидимая и полностью воспроизводящая исходный
   симптом.
