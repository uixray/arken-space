# Ключевые UX-сценарии — аудит исходников и исправления

Дата: 21.11.2026. Объём: текущий технический first-run из `docs/first-run.md`: аккаунт мастера, создание кампании, подготовка стола, личное приглашение, вход игрока и персонаж. Это не новое маркетинговое позиционирование и не приёмка будущих 3D/P2P-возможностей.

## Уровень свидетельств

Аудит выполнен по исходникам и связанным состояниям. До/после ниже — изменения кода и предусмотренного им интерфейса, а не результаты запуска приложения. Приоритеты — оценка риска для указанного сценария, не статистика пользователей. Тесты, сборка, browser/device QA и измерения не выполнялись по указанию владельца. Наличие live-регионов и touch-размеров в коде не означает подтверждённую доступность на устройстве или соответствие WCAG.

## Приоритизированные находки и исправления

| Приоритет | Проблема в исходном состоянии | Исправление | Источник после изменения |
|---|---|---|---|
| P1 | После отказа `CampaignRouter` предлагал только уход в аккаунт. Отклонённый promise оставался в ref: собственного повтора открытия не было. | Явный повтор сбрасывает задачу и запускает новую попытку; существующий StrictMode guard сохраняется на одну попытку. Некорректная ссылка получает отдельное объяснение и путь к аккаунту. | `CampaignRouter.tsx` |
| P1 | Desktop-статус соединения и действие восстановления спрятаны в меню сеанса; на компактной карте сам header скрыт. Последний snapshot можно принять за актуальную игру. | Общая видимая панель сообщает о соединении/синхронизации, даёт ручное восстановление и прямой путь к аккаунту/входу при повторном отказе. Отдельная строка layout; высота учитывается body-порталом персонажей. | `ConnectionNotice.tsx`, `connection-notice.css`, `App.tsx` |
| P1 | Обработчик восстановления всегда выставлял RESYNCING и вызывал emit даже у отсоединённого сокета. Он не запускал `connect()`, а при null socket оставлял ложное ожидание. `connect` сразу объявлял ONLINE до нового snapshot. | При отсутствии сокета — объяснение; при разрыве — `connect()` без буферизации resync; при подключённом транспорте — запрос актуального состояния. Ручные попытки ограничены частотой. ONLINE выставляется после канонического snapshot/delta; connect_error обновляет статус. | `App.tsx`, `use-game-socket-subscriptions.ts` |
| P1 | Ссылка приглашения выводилась общей ссылкой под списком, без имени кампании/игрока и без действия копирования. Переход по ней самим мастером мог спутать сценарии приглашения и присоединения. | Результат подписан кампанией и получателем; отдельное поле и явное копирование. При отказе Clipboard поле выделяется для ручного копирования. Успех сообщается только после ответа Clipboard API. Создание приглашения повторно не вызывается. | `AccountInviteLink.tsx`, `AccountAuthWorkspace.tsx` |
| P2 | Результат приглашения ниже списка трудно обнаружить с клавиатуры; переход фокуса после фатальной ошибки не определён. | Фокус на результате только если пользователь сохранил исходное положение фокуса; без автоматического объявления секретного URL. При фатальной ошибке фокус получает заголовок и доступен выход в «Мои кампании». | `AccountInviteLink.tsx`, `AccountAuthWorkspace.tsx`, `AppErrorBoundary.tsx` |
| P2 | Иконка карточки кампании была текстовым глифом. | Переиспользован канонический SVG `MapSurfaceIcon` через `AppIcon`. | `AccountAuthWorkspace.tsx` |

В этом ограниченном статическом разборе не установлено новых доказанных P0. Это не утверждение, что во всём продукте нет P0/P1. Выявленные выше P1 исправлены на уровне реализации; runtime-результат остаётся неподтверждённым.

## Материалы «до/после» для кейса

| До | После | Какую цель можно обоснованно описать |
|---|---|---|
| Ошибка открытия → только возврат к выбору кампаний | Ошибка открытия → явный повтор или выбор кампании | Сократить навигационный тупик после временного отказа |
| Скрытый статус/emit в offline socket | Видимый recovery banner; connect при разрыве; ONLINE после snapshot | Разделить транспорт, синхронизацию и актуальное состояние |
| Неподписанный URL-переход под списком | Кампания + получатель + копирование + ручной fallback | Уменьшить риск отправки приглашения не тому игроку/кампании |
| Фатальный экран с двумя попытками восстановления | Фокус на ошибке и дополнительный путь к аккаунту | Оставить понятный выход при повторяющемся сбое |

Иллюстрация состояний: `.qa-temp/ux-closure-20261121/before-after.html`. Это локальная статическая схема, явно не скриншот приложения; данные и ссылка в ней вымышлены/скрыты. Хеши текущих исходников — рядом в `source-hashes.txt`.

Для portfolio допустимо показывать эти решения и реальные изменения исходников. Нельзя называть их результатами usability study, публиковать вымышленные улучшения скорости/конверсии, выдавать схему за реальный screenshot или переносить старый PASS на новые байты.

## Сознательные ограничения

* Текущий scope — базовая игра на Аркен-Хар. Позиционирование, полное оформление/publish portfolio case и исследование на людях остаются самостоятельными задачами проекта; этот кодовый аудит не закрывает их.
* Recovery уведомляет о последнем полученном состоянии, а не обещает полноценное offline-редактирование. Политики сохранения черновиков, команд и серверных ревизий не переписаны.
* Ручное копирование сохраняет ссылку только в памяти UI/буфере пользователя; секрет не попадает в отчёт, storage или диагностику. Уже отправленное приглашение/содержимое Clipboard этим UI не отзывается.
* Физические устройства, assistive technologies, визуальные темы/контраст, реальные сетевые отказы и пользовательская приёмка остаются непроверенными для этих байтов. Закрытие текущей задачи — по исходникам и реализации при указании владельца работать без тестов, не сертификация и не публикация.
