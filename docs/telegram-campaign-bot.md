# Telegram-бот кампании: первая версия

## Объём, утверждённый владельцем 21 ноября 2026

- Вопросы о кампании: ограниченная справка по интерфейсу и поиск в доступных
  игрокам статьях мира. При отсутствии источника бот прямо сообщает об этом.
- Свои или управляемые персонажи: список, характеристики и навыки в личном диалоге.
- Публичные броски через прежний серверный обработчик и общий журнал.
- Изменения персонажа через приватную заявку мастеру. Мастер рассматривает её
  и применяет значения в приложении; бот не пишет характеристики без этого шага.
- Баги и вложения — через уже существующий intake, проверку и перенос в Linear.

Синхронизация STORY не входит в первую версию. Бот не является генеративным
ассистентом и не придумывает ответы или скрытые сведения. Эта реализация
локальная; новые сборка, тесты, миграция и живая доставка не выполнялись.

## Подключение для пользователя

Панель «Telegram-бот» находится в меню сеанса на компьютере и в компактном
мобильном меню. Пользователь открывает личный диалог с настроенным ботом и
получает свой числовой Telegram ID командой `/whoami`.

В панели создаётся одноразовый код на пять минут, связанный с конкретным
Telegram ID и текущим сеансом приложения. Код хранится в БД только как hash;
в очереди `/link` также сохраняется только hash, не исходный bearer-код.
Команда показывается только в ответе владельцу и очищается при закрытии панели,
изменении адресата или смене campaign/membership/role.

Для группы мастер сначала добавляет туда бота и получает ID чата и темы
командой `/where`. Код группы подходит только указанным пользователю, группе
и теме. Чужая группа не может присоединиться этим кодом. На кампанию допускается
одна активная группа/тема; занятую другой кампанией группу нельзя молча переназначить.
Приватные темы Telegram в этой версии не поддерживаются: личный диалог — без темы.

Привязка намеренно **сеансовая**. Выход, истечение сеанса, отзыв доступа или
отключение исходного аккаунта/приглашения прекращают доступ бота. Смена роли
проверяется заново, включая GM-владельца группы. Для подключения после нового
входа создайте новый код. `/unlink` отключает личную привязку; кнопка в приложении
также отключает группу, созданную этим сеансом, и его неиспользованные коды.

## Команды

| Команда | Действие |
| --- | --- |
| `/help` | Список команд |
| `/campaign` | Название и игровой день |
| `/ask вопрос` | Подтверждённая справка и доступные статьи мира |
| `/characters` | Страница из 20 доступных персонажей и команда следующей страницы, только лично |
| `/character UUID` | Характеристики и навыки доступного персонажа, только лично |
| `/roll 1d20+2` | Публичный серверный бросок с сохранением результата |
| `/change UUID описание` | GM_ONLY-заявка игрока, только лично; применение мастером в приложении |
| `/bug описание` | Запись в утверждённой группе багов; можно прикрепить поддерживаемые файлы |
| `/unlink` | Отключение своей личной привязки |

Длинная сводка ограничивается размером ответа с явной пометкой сокращения;
полный лист и полный журнал доступны в приложении. Итог броска расположен до
подробностей результата, чтобы сокращение не убирало главное число.

Бот не публикует карточки или заявки в группе. Даже вопрос мастера в группе
использует PLAYER-visible материалы мира, а не GM-only текст. Вложения в
игровых командах не исполняются; пересланные команды, сообщения других ботов и
команды с чужим `@botname` игнорируются. Правки игровых команд не изменяют
уже выполненное действие. Удаление Telegram-сообщения не отменяет бросок или заявку.
Правки, файлы и альбомы багов сохраняют существующий review-процесс intake.

## Очередь и идемпотентность

Webhook аутентифицирует секретный заголовок constant-time сравнением, ограничивает
тело 256 KiB и частоту 120 запросами/минуту. До подтверждения сохраняется durable
receipt. Есть уникальные ключи receiver/update и receiver/chat/thread/message;
канонический hash сообщения различает повтор и коллизию. При коллизии старое
сообщение не переписывается, возвращается 409; при заполнении очереди — 503.
Одновременно допускается до 1000 ожидающих/обрабатываемых команд и ответов на receiver.
Исторические receipts автоматически не удаляются.

Sealed receipt фиксирует исходный сеанс **при приёме**, поэтому смена привязки
до обработки не перенаправляет старую команду в другую кампанию. Worker выполняет
команды последовательно, CAS переводит PENDING → RUNNING → DONE/UNKNOWN.
Длительная транзакция inbox не удерживается во время канонического HTTP-вызова.

Внутри используются короткоживущие backend-only delegate sessions с исходным
provenance. Токен не хранится в Telegram-таблицах, не передаётся в Telegram и
удаляется из sessions в finally. HTTP-операции по-прежнему проходят requireAuth,
campaign ACL и каноническую валидацию. Delegate имеет срок не более 30 секунд.
Повтор `/roll` для того же receipt читает исходный `dice.created` и не вычисляет
новый результат. Заявка использует прежний actionId/idempotency механизм.

Ответы имеют отдельные PENDING/SENDING/SENT/FAILED/UNKNOWN/CANCELLED состояния.
Перед отправкой повторно проверяются действующая привязка, сеанс, кампания и
владелец группы. Смена привязки/отзыв доступа отменяет ещё не отправленный ответ.
Уже начатый сетевой запрос нельзя гарантированно отозвать задним числом.
Sender ограничивает темп по чату, имеет 15-секундный timeout и bounded response
64 KiB. Сообщение — plain text без автоматического HTML/Markdown parsing.

При неизвестном сетевом результате автоматической повторной отправки нет:
Bot API не предоставляет здесь общего exactly-once ключа. В панели показываются
только команды, время и состояния **этого сеанса**, без чужого приватного текста.
Владелец может восстановить обработку после подтверждения остановки прежнего
обработчика, повторить отказанную доставку или сверить UNKNOWN с Telegram.
Повтор UNKNOWN требует подтверждения, что прежний worker остановлен и ответа
нет; полученный ответ можно подтвердить вручную без выдуманного message ID.

Оставшиеся после падения RUNNING/SENDING записи не переисполняются вслепую.
Содержимое чужой переписки не доступно через обычную GM-панель. Восстановление
не является доказательством автоматически проверенной exactly-once доставки.

## Баги и вложения

Повторно используются `persistTelegramBugUpdate`, `createBugIntakeDrain` и
`createTelegramBugFileSource`, прежние альбомы, исходные ссылки, review и Linear
outbox. Сырые баги принимает только заданный `TELEGRAM_CAMPAIGN_BUG_CHAT_ID`.
Команда подтверждает попадание в очередь, а не создание задачи Linear до review.
Нет второго автоматического отправителя в Linear.

Файловый worker отделён от очереди игровых ответов. Лимит Bot API-файла — не более
20 MiB, private-кэша — 1 GiB; при необходимости сверки файловый drain приостанавливается
с безопасным диагностическим событием. После штатного разбора/reconciliation нужен
перезапуск его lifecycle. Код использует прежние устойчивые состояния файлов.

На receiver должен работать один владелец file-drain. Прежний ручной polling/drain
нельзя запускать параллельно с активированным worker. При переходе с личной
Telegram-сессии надо сверить receiver/origin и совместимость уже сохранённых
file IDs; это не проверено автоматически этой реализацией.

## Отдельная активация оператором

По умолчанию `TELEGRAM_CAMPAIGN_ENABLED=false`. Панель сообщает о выключенном
боте; код не создаёт бота, не вызывает setWebhook и не меняет окружение сам.
Для первого включения нужны отдельное разрешение владельца, тестовый бот и
синтетическая кампания. Production activation — отдельный gate.

Подготовленные настройки:

- `TELEGRAM_CAMPAIGN_ENABLED=true` — только в HOSTED режиме;
- `TELEGRAM_CAMPAIGN_RECEIVER_ID` — согласованный UUID существующего bug receiver;
- `TELEGRAM_CAMPAIGN_USERNAME` — проверенное имя именно этого бота;
- `TELEGRAM_CAMPAIGN_TOKEN` — его приватный Bot API token;
- `TELEGRAM_CAMPAIGN_SECRET` — независимый случайный секрет 32–256 символов;
- `TELEGRAM_CAMPAIGN_BUG_CHAT_ID` — согласованная группа багов;
- `BUG_INTAKE_ENABLED=true` и абсолютный private `BUG_INTAKE_ROOT`.

Миграция `0091_telegram_campaign_bridge` следует за подготовленной `0090` и
поставляется вместе с schema/API/web. До включения следует отдельно сверить
bot ownership, TLS, редактирование секретов в HTTP/proxy журналах, staff allowlist,
права/каталог приватного кэша и единственный file-worker. Webhook URL:
`/api/integrations/telegram/campaign`, секрет — в `X-Telegram-Bot-Api-Secret-Token`,
никогда в URL. Browser APIs дополнительно сверяют текущие campaign и membership;
mutation требует точного WEB_ORIGIN.

Выключение флага прекращает регистрацию receiver/worker. Server shutdown
останавливает workers до закрытия БД; ожидание файлов ограничено существующим
timeout источника, прерванные операции могут потребовать сверки.

## Граница готовности

Реализован согласованный код первой версии. По запросу владельца выполнен разбор
исходников вместо новых прогонов. Runtime, миграция, живой Telegram, browser UI,
поведение после аварии и сетевые пределы на новых байтах не подтверждены запуском.
Эта документация и закрытие реализации не являются утверждением о публикации
или эксплуатационной квалификации.
