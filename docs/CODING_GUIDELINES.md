# Правила архитектуры и написания кода в Arken Space

> Статус: Действующий архитектурный стандарт
> Область применения: `apps/web`, `apps/server`, `packages/*`
> Основная цель: предотвращение повторного разрастания монолита `App.tsx`, обеспечение нулевой стоимости рендеринга действий и защита высокой производительности игрового стола.

---

## 1. Контекст проблемы: почему разрастался `App.tsx`

Исторически `App.tsx` дважды разрастался до критических размеров (3 389 строк в ревизии `321b86d`, затем после этапов A/B снова до 2 865 строк).
Анализ показал 5 конкретных причин этого рецидива:

1. **Инлайновые модальные окна и диалоги:** Каждая новая фича добавляла в `App.tsx` свой `useState(false)` и 30–60 строк JSX (`<ArkenDialog>`, `<TextPromptDialog>`), часть из которых со временем становилась сиротами (например, забытый `createSceneOpen`).
2. **Инлайновые доменные блоки интерфейса:** Блоки вроде лотка токенов (`<details className="token-tray">`), переключателя сцен (`<details className="scene-picker">`) и шапки приложения встраивались прямо в тело разметки `App.tsx`.
3. **Прямые мутации через `api(...)`:** Вызовы API прямо из обработчиков клика внутри JSX без изоляции в хуках.
4. **Огромный блок сокет-подписок:** Сотни строк `socket.on(...)` с инлайновыми колбэками внутри гигантского `useEffect`.
5. **Нестабильные стрелочные функции в пропсах:** Инлайновые колбэки приводили к инвалидации `React.memo` по всему дереву компонентов.

---

## 2. Ключевые архитектурные правила

### Правило 1: Принцип чистой композиции приложения (Composition Root)

`App.tsx` является **исключительно корнем композиции** (Composition Root).

- **Что разрешено в `App.tsx`:**
  - Верхнеуровневые провайдеры контекстов (`CampaignActionsContext.Provider`, `RollVisibilityContext.Provider` и др.).
  - Вызов агрегирующих хуков оркестрации (`useCampaignActions`, `useHotkeys`, `useGameSocketSubscriptions`).
  - Верхнеуровневый каркас разметки (`AppShell`, `AppHeader`, `Workbench`, `AppModals`).
- **Что категорически запрещено в `App.tsx`:**
  - Прямой рендеринг модальных окон и диалогов (выносить в `AppModals.tsx` или в доменные компоненты).
  - Инлайновые доменные панели (выносить в отдельные компоненты: `TokenTray.tsx`, `AppHeader.tsx`, `ScenePicker.tsx`).
  - Прямые вызовы `api(...)` (только через хуки действий `use*Actions`).
  - Инлайновые обработчики сокетов `socket.on(...)` (только через специализированные хуки синхронизации).
  - Локальные `useState` для управления отдельными диалогами.

> **Лимит размера:** Файл `App.tsx` не должен превышать **800 строк кода**. Превышение лимита блокируется архитектурным тестом.

---

### Правило 2: Изоляция модальных окон (Modal Isolation)

Модальные окна, диалоги и всплывающие формы **никогда не инлайнятся в `App.tsx`**.

Существует два разрешённых места размещения диалогов:

1. **Колокация в фиче:** Если диалог логически привязан к конкретному компоненту (например, выбор ассета внутри поля ввода или управление сценой внутри менеджера сцен), он живёт внутри этого компонента.
2. **Агрегатор глобальных окон (`AppModals.tsx`):** Если диалог открывается из разных мест приложения (например, шорткаты, смена темы, переименование кампании, передача хода игроку), он подключается в `AppModals.tsx`.
   - Состояние открытия диалогов управляется типизированным объектом модалей или стейт-хуком, а не десятком разрозненных `useState` в корневом компоненте.

---

### Правило 3: Изоляция мутаций в хуках доменных действий (Domain Action Hooks)

Любая мутация серверного состояния, REST API вызов или отправка сокет-команды выносится в соответствующий доменный хук:
`useSceneActions.ts`, `useCampaignActions.ts`, `useTokenDefinitionActions.ts`, `useChatActions.ts` и т.д.

Доменные действия регистрируются в `CampaignActionsContext`.

#### Жёсткий инвариант контекста действий:

> **В `CampaignActionsContext` запрещено передавать любые изменяемые данные (state, snapshot, id, флаги).**

_Контекст в React не имеет избирательной подписки (fine-grained subscription)._
Если положить в контекст действий реактивное значение (например, `snapshot`), любой компонент, читающий этот контекст, будет принудительно перерисовываться при каждом игровом событии.
Поскольку в контексте хранятся **только функции**, ссылка на объект контекста стабильна на всё время жизни приложения, и стоимость его использования равна **ровно нулю**.

---

### Правило 4: Паттерн стабильности ссылок (`latestRef`)

Для сохранения высокой производительности (60 FPS при перемещении токенов, анимациях тумана войны и бросках кубов) тяжёлые компоненты обёрнуты в `React.memo`.

Чтобы `React.memo` не инвалидировался впустую:

- **Запрещено** добавлять `snapshot`, `activeScene` или другие быстро меняющиеся объекты в список зависимостей `useCallback` обработчиков. Если добавить `snapshot` в `deps`, функция будет пересоздаваться на каждый чих сервера.
- **Обязательно** использовать паттерн `latestRef`:
  ```tsx
  // Актуальное состояние пишется в ref на каждом рендере:
  const snapshotRef = useRef(snapshot);
  snapshotRef.current = snapshot;

  // Обработчик создается ОДИН РАЗ и читает актуальные данные из ref:
  const handleUpdate = useCallback((id: string) => {
    const current = snapshotRef.current;
    // ... работаем с актуальным snapshot ...
  }, []); // пустые deps — ссылка функции никогда не меняется!
  ```

---

### Правило 5: Изоляция сокетов реального времени (Socket Segregation)

Все обработчики входящих сокет-событий (`game:patch`, `presence:sync`, `dice:roll`, `chat:message` и др.) выносятся из `App.tsx` в специализированный хук синхронизации (например, `useGameSocketSubscriptions.ts`).

- `App.tsx` только вызывает хук, передавая ему необходимые стабильные диспетчеры или ссылки.
- Никаких сотен строк с `socket.on(...)` внутри тела `App.tsx`.

---

### Правило 6: Запрет заимствования типов через `Pick<SidebarProps, ...>`

Компоненты и хуки не должны заимствовать типы сигнатур друг у друга через `Pick<Props, ...>`.

- Контракты данных берутся из `@arken/contracts`.
- Контракты действий объявляются в интерфейсах самих доменных хуков (`SceneActions`, `ChatActions` и др.).
- Это предотвращает скрытое превращение типов в `unknown` при рефакторинге пропсов.

---

### Правило 7: Автоматизированный контроль инвариантов

Правила не должны оставаться только на бумаге. Они защищаются автоматическими тестами:

1. **Тест на чистоту функций контекста:** `campaign-actions-context.test.tsx` рекурсивно проверяет, что каждый элемент контекста является функцией. Любое нефункциональное значение ломает CI.
2. **Архитектурный лимит размера:** `apps/web/src/architecture.test.ts` проверяет размер ключевых файлов (включая лимит `App.tsx`) и запрещает прямое использование `api(` в файлах-композиторах.

## 3. Чек-лист перед коммитом изменений в UI

Перед отправкой изменений в репозиторий ответьте на вопросы:

- [ ] Не добавил ли я новый `useState(boolean)` для диалога в `App.tsx`?
- [ ] Не добавил ли я JSX модального окна прямо в разметку `App.tsx`?
- [ ] Не вызываю ли я `api(...)` прямо из разметки вместо вызова метода из `CampaignActionsContext`?
- [ ] Стабильны ли ссылки на переданные колбэки (использован ли `latestRef` при обращении к `snapshot`)?
- [ ] Зелёные ли `tsc --noEmit` и `pnpm test`?
