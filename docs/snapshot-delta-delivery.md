# Передача изменений редких действий

## Протокол v1

Клиент объявляет `snapshotDeltaV1: true` в Socket.IO handshake. Это только
согласование формата доставки, не право доступа. Сервер по-прежнему строит
каноническую проекцию через `buildSnapshot` отдельно для каждого получателя.
После этого сравниваются сериализованные поля верхнего уровня с последней
отправленной этому сокету канонической проекцией.

Первый `game:snapshot` содержит полный снимок и необязательный второй аргумент
`deliveryId`. При следующих маршрутных рассылках `game:delta` передаёт:

- `baseId` — ID предыдущей доставки;
- `id` — ID новой доставки;
- `changes` — полные замены только изменившихся полей;
- `removed` — поля, исчезнувшие из проекции.

Списки заменяются целиком, а не объединяются по ID: скрытие жетона, отзыв доступа
и удаление вложения не должны оставлять прежнюю запись у получателя. Активная
сцена, ассеты, подписи, очередь и видимость поступают из того же построителя,
что и до оптимизации. Поэтому не требуется отдельная модель прав для редких
действий или объединение нескольких независимых per-row watermark.

Охвачены существующие маршрутные рассылки, в том числе инициатива, слой,
видимость и размер жетона, имя/портрет персонажа, сцены, undo/redo, кошелёк и
штампы. Если изменение затрагивает ассеты, соответствующее поле тоже входит
в delta. Общая очередь coalescer и точечные события частых действий сохранены.

Клиент хранит базовую каноническую проекцию отдельно от изменяемого point events
и preview состояния React. Сначала из неё собирается новый полный образ, затем
он проходит прежний `reconcileGameSnapshot`. Применять patch прямо к текущему
React-состоянию нельзя: пропущенные неизменившиеся поля могут отличаться от
локального preview или промежуточного point event.

## Совместимость и восстановление

- Клиент без capability получает прежний полный снимок без ID.
- Новый клиент работает со старым сервером: полный снимок без ID сбрасывает базу.
- Подключение, восстановление и явная смена рассматриваемой сцены устанавливают
  новую полную базу. Несовпадение `baseId` вызывает переподключение с bootstrap.
- Смена кампании, membership или роли требует полной доставки.
- Слишком большой снимок и patch не меньше полного снимка доставляются целиком.
- Откат клиента или сервера не требует изменения БД.

## Ресурсы и ограничения

Кэш изолирован по экземпляру сервера и socket ID; disconnect очищает запись.
Пределы: 8 MiB сериализованной проекции на сокет, 64 MiB на экземпляр сервера,
1024 базы; при вытеснении следующая доставка полная. Это лимиты объёма
сериализованных данных, не обещание точного размера JS heap. Содержимое проекций
и идентификаторы доставки не записываются в диагностические журналы.

Оптимизация сокращает сетевой payload, когда сериализованный patch меньше
полного снимка. Она **не устраняет сборку снимка или запросы к БД** и не является
пообъектным протоколом каждого домена. Старые snapshot metrics измеряют объём
канонической проекции до transport-оптимизации, не фактический размер delta на
проводе. Численный выигрыш, задержка и нагрузка здесь не утверждаются.

Решение владельца от 21 ноября 2026 разрешает реализацию без новых замеров;
текущий пул ограничен кодом без тестовых прогонов. Изменения локальные,
публикация и эксплуатационная приёмка отдельно.
